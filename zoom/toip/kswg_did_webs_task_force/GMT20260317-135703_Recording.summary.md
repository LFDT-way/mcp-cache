## Overview

The meeting focused on two main topics: the DID Web S specification development and foreign artifact handling in ACDCs. Jonathan and Kent provided updates on their progress refining the DID Web S spec, clarifying the lifecycle of DID documents and transformation rules between DID Web and DID Web S versions. The group discussed technical challenges around URL formatting and resolver behavior, particularly regarding how to signal different DID types to HTTP servers. Daniel then presented his work on a foreign artifact schema proposal, which aims to provide a standardized mechanism for bridging external content like photos or credentials into ACDCs, though concerns were raised about semantic equivalence and security implications of using signatures versus hashes for identification.

### Diglavis Specification Progress Update

Jonathan reported progress on the Diglavis specification, noting that he and Kent have been working on it for the past week. They clarified the lifecycle of DID Web documents, explaining how DID Web resolvers and DID Web S resolvers interact with each other. The team has completed work on read and update operations and is currently focusing on the remaining CRUD operations, with plans to finish the rest of the examples in the document.

### DIDWeb Repository Updates Discussion

The team discussed updates on resolving terminology references and repository changes, with the repo now named KSWG. Jonathan and Kent outlined plans to prepare a draft for review by Sam and Phil within the next couple of weeks, followed by a vote from the working group before submitting to the steering committee. Samuel raised questions about verifying the authenticity of DIDWeb documents, particularly concerning potential spoofing by malicious resolvers. Jonathan explained that verification relies on the DIDWeb resolver transforming the document and providing the necessary credentials for validation.

### DIDWEB vs DIDWEBS Documents

The team discussed the differences between DIDWEB and DIDWEBS documents, clarifying that a single did.json file cannot contain both document types due to technical constraints in how resolvers handle URLs. Kent explained that when a DIDWEBS document is presented to a DIDWEB resolver, it will return the appropriate DIDWEBS document through the standard did.json endpoint, as long as the resolver is authorized to handle DIDWEBS. Jonathan confirmed that publishing a DIDWEBS document is possible through transformation from a DIDWEB document, though this requires additional resolution steps beyond the standard did.json endpoint.

### DID Specification URL Transformation Gap

The team discussed a gap in the DID specification regarding how an HTTP server can determine which type of DID document to serve when requested. Jonathan and Samuel explained that the current URL transformation process replaces the "did:" prefix with "https:" and doesn't include the original DID in the URL. Kent and Jonathan proposed asking Marcus about whether there's an accepted practice of using path or query parameters to signal the original DID to the server, which would allow for direct serving of the appropriate DID document without requiring two resolution steps. The team agreed this represents a legitimate gap in the specification that should be addressed either normatively or informatively.

### DIDWebS Query Parameter Discussion

The team discussed adding a query parameter to HTTP URLs to signal whether a DIDWebS DID document is being requested, rather than requiring a two-step process through a DID resolver. Samuel clarified that while this use case is legitimate, consumers would still need to verify the key state themselves since they cannot trust all DID resolvers. The group agreed this feature could be easily added to both the specification and resolvers, with Jonathan suggesting they should check with Marcus about standardized approaches used by other DID methods.

### Foreign Artifact Schema Proposal

Daniel presented a proposal for a foreign artifact schema to enable bridging external content into ACDCs, using examples like photos and digital credentials. He explained how this would work through a Content Identifier field with MIME types and additional metadata, while ensuring secure references using SEDs or hashes when native signatures aren't available. The group discussed how this would integrate with the dossier spec, with Daniel clarifying that foreign artifacts would be cited from within the ACDC rather than the other way around, and emphasizing the need for careful semantic handling when incorporating external credentials into ACDCs.

### ACDC Digital Container Security Discussion

Samuel and Daniel discussed the use of ACDC (Attribute-CSV Digital Container) as a container for digital artifacts, focusing on how to handle hashing and signatures, particularly when dealing with W3C verifiable credentials. Samuel expressed concerns about using signatures due to potential security weaknesses, suggesting that hashing might be a safer approach. They considered treating ACDC purely as a container, hashing the content without imposing additional semantics. Samuel also introduced the concept of blinding hashes to maintain privacy while allowing verification. The discussion concluded with an agreement to update the PR based on these insights, aiming to achieve a balance between simplicity and security.

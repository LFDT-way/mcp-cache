## Overview

The KERI Stack Working Group meeting focused on finalizing specifications and addressing version control processes. The group discussed the need to update contributor lists across three specifications and agreed to use GitHub's contributor feature to track contributions. They explored options for assigning DOIs to the specifications through Zenodo, with Carly explaining the process and potential challenges. The team also reviewed changes to the DID Web S specification and its upcoming review period. Samuel announced that the steering committee had approved the KERI specifications, marking a significant milestone after five years of work. The conversation ended with discussions about releasing version 1.0 of the specifications and the need to establish a process for future versioning and DOI assignments.

## Details

### GitHub Repository Licensing Consistency

The team discussed GitHub repository licensing issues, where Carly identified that the KERI specification had the correct license files while CSER and ACDC specifications were missing license files. Samuel confirmed that the KERI specification was properly formatted with both a license.md file and a license file, while the other specifications only had the license.md file. The team agreed to add the missing license files to the CSER and ACDC specifications to ensure consistent licensing across all repositories.

### Release Issues and Membership Challenges

The team discussed issues with the 1.0 release, including incorrect contributor listings and the need to update release tags and README links for both the final release and editor's draft. Carly agreed to investigate why new members cannot join Trust Over IP as free individuals since January, as this has affected KERI Foundation members who can now only join through the Linux Foundation as a workaround.

### KERI Repository Link Correction

Phil added a new item to the KERI repo and discussed the need to fix a link that was incorrectly categorized under the Technical Stack Working Group instead of the KERI Suite Working Group. Kent agreed to create an issue to address this, and Phil added it to his to-do list. The team also discussed the need to improve the acronyms used in the repo, deciding to change "VD" to "VRDOS" and "SID" to "SID URN." Samuel asked if future topics were being tracked, but Phil couldn't recall and suggested they might need to start doing so.

### KERI Foundation's Strategic Updates

The steering committee approved the specs, which are now formally adopted and require cleanup of releases. Samuel announced the first annual KERI conference scheduled for April 21-23, coinciding with a SETI summit hosted by the state of Utah. He also noted that the KERI Foundation is an associate member of the Linux Foundation under the LF Decentralized Trust Umbrella, while the Trust Over IP Foundation is now a project under the same umbrella. Carly sought clarification on the Linux Foundation's governance models, highlighting the organization's innovation in decentralized governance.

### KERI Specification and Conference Updates

The team discussed updates on the KERI conference program with new speakers and sponsors, and Kent announced that version 0917 of the DIDWebS specification is under review by the broader KERI stack working group, with a 60-day review period ending on April 4th. Jonathan requested to hold the formal announcement of the specification's readiness until next week after completing a thorough review. Samuel mentioned ongoing work to remove technical debt in the KERI code, which involves replacing legacy methods with higher-level abstractions, and warned that these changes might break code relying on low-level database calls.

### Cram Implementation and Library Updates

Phil suggested deprecating instead of deleting certain methods in Baser for a few releases, but Samuel noted that changes are easy to make and downstream users like KERI might need to migrate. Ari mentioned dedicating himself full-time to Cram after finishing Multisig for a healthcare project, and Phil confirmed this. Samuel shared that he had refactored Cram's implementation with Ari, resulting in a simpler and more elegant design detailed in the cram.md file. Samuel also provided an update on HEO, a library KERI depends on, noting progress on basic authentication for signing mammograms and plans to refactor and work on acknowledge messaging for reliability.

### Signify TS-KERIA Code Integration

The team discussed merging the Signify TS codebase with KERIA, aiming to ensure that changes in KERIA automatically propagate to Signify TS. Kent explained that the integration would involve two top-level directories, maintaining separation while sharing the source repository. The team decided to start with Signify TS and potentially incorporate Signify Pi later, due to resource constraints and familiarity with the codebase. Kent also reported updates on DID Web S, including corrections to multi-sig thresholds and clarifications on the "also known as" section, with the latest changes available for review.

### DOI Registration Process Discussion

The team discussed the process of obtaining a permanent URL for the URN registration, with Carly explaining the benefits of using the DOI system through Zenodo, which is operated by CERN and offers free persistent identifiers. Samuel raised questions about the cost and process of creating DOIs, and Carly clarified that it is free for them and involves an automated system that generates DOIs for version releases. The team decided to add a discussion item about including the DOI in the spec or README, with Samuel suggesting they pre-mint a DOI for the 1.0 draft release. Carly mentioned a workaround for pre-releasing in Zenodo, and Phil noted the irony of not using a set. The conversation ended with Carly offering to work with Henk and Corr on releases and DOIs once the timing is confirmed.

### Contributor Recognition and Specification Updates

The team discussed contributor recognition for three specifications, agreeing to use GitHub's contributor list based on accepted pull requests. They decided to create issues for each repository allowing community members to add their names if they feel they contributed but aren't listed. Carly is investigating the process for manually registering DOIs, which will be added to the specifications before the official V1.0 release. The team also identified that license files for two specifications need to be updated to match the KERI spec, with issues already created for this task.

### Version Control and Release Planning

The team discussed version control and release processes for their specifications. Samuel and Henk aligned on creating a 1.0 release version that would be snapshot and rendered separately from the ongoing 1.1 draft version, allowing for continued contributions to the draft while maintaining a fixed release version. Carly raised questions about GitHub releases and DOIs, leading to a discussion about Zenodo account ownership and governance, with Carly offering to help Henk set up the DOI and potentially share access with multiple community members.

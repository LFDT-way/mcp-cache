### Caesar Encoding for Image Embedding

Samuel discussed the use case of embedding photographs in a contact wallet using Caesar encoding. He proposed leveraging media types to send images without creating separate primitive codes, suggesting the use of group codes with a four-field structure. Samuel explained the process of creating a blinded set by calculating the digest of a quadruple and replacing certain elements with dummy characters. He emphasized that this approach allows for embedding images as field values in messages, distinguishing it from attachments.

### Media Attachment Cryptography Format

Samuel explained the structure of a message format that includes media attachments. He described how a cryptographic reference (Said) is used to ensure the integrity of attached media, and explained that the media type is encoded using a Labeler class that efficiently handles both base64 and non-base64 characters. The format includes a salty nonce or UUID field, which can be empty if blinding is not desired, and the media itself is encoded using Caesar-compatible base64.

### Media Attachment Encryption Process

Samuel explained how to handle media attachments in messages by using a group with a said (secure attribute) that contains the media, allowing for encrypted storage and verification. Phil clarified his understanding of the process, confirming that the said would be the same for non-blinded images and that the actual media is encoded as text in the fourth field. Samuel emphasized that this method extends the principles used for blinded state tells and involves creating attachments before messages, which is not problematic.

### Secure Media Attachments for Keri

Samuel explained a proposal to securely attach media files to Keri messages, similar to how attachments work in email. He described how the system would use a "salty nonce" and Caesar encoding to ensure security and compatibility with existing message formats. The parser would need to be updated to handle these attachments, which could contain multiple media types like PNG, JPEG, and TIFF. Samuel emphasized that this would replicate the functionality of email attachments in a secure manner.

### Caesar Code Security Feature Implementation

Samuel presented a new security feature that allows attachments to be encrypted with Caesar codes, making them tamper-proof and verifiable. He explained how this could be used to secure email attachments and prevent database duplication. Jeff suggested using the cryptographic digest as a watermark to address issues with AI-generated content. Samuel also discussed the security vulnerabilities in large language models, highlighting how simple, non-cryptographic symbols are used for API interactions. The group agreed to move forward with implementing this security feature, with Phil giving it a thumbs up.

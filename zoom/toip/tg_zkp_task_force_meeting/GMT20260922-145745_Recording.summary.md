## Overview

The meeting focused on updates and progress regarding the ZKP (Zero-Knowledge Proof) specification and implementation, with participants discussing recent developments, review processes, and next steps. Mitchell provided updates on the spec merge and rendering, including refinements to separate cryptographic background from book aspects and create a more condensed specification. ## Details

### ZKP Specification Progress Review

The team discussed recent progress on the ZKP specification, with Mitchell reporting that round one review of the draft SHAFE is targeting completion and that pull request 11 was merged with refinements to separate cryptographic background from implementation aspects. The group addressed where to host educational documentation, with Drummond suggesting an implementation guide could be created using SpecUp T in the ZKP Task Force repo, and Mitchell agreed to coordinate with Jeff Turk on setting up this guide.

### Spec Implementation and Review Progress

The team discussed following Jeff's template for the spec and confirmed that implementation guides can be less rigid than official publications. Scott reviewed the status of Round One, noting that four requirements including construction record structure and field name mapping have been completed, with records now carrying a review slot for sign-off. The team was asked to review and file their evaluation using the provided form with reasons for their assessment.

### Documentation Review Preparation Meeting

The team discussed preparations for an upcoming review of their documentation by the kernel team in two weeks. Mitchell reported removing cookbook jargon from the guide and suggested creating a refined README with explicit navigation and a composed list of numbered constructions. Drummond asked about whether the spec should include all constructions or reference a registry, with Mitchell indicating a preference to incorporate constructions directly into the ZKP spec rather than using a separate registry.

### Construction Specifications and Prototype Updates

The team discussed specifications for constructions and agreed to start with a core set in the spec, with the possibility of creating a registry later as examples expand. Mitchell noted that ZKP implementations could be integrated natively into the OpenVGC repository. Scott provided an update on Record 023, reporting that Glenn and the Berkeley team successfully built a working prototype for an admission proof using the PCS library, resulting in a 1.4 kilobyte proof that verifies five vetters in 12 milliseconds, with 426 library tests passing and no changes needed to the policy engine.

### ZKP Implementation Conference Preparation

Drummond shared exciting news about the first ZKP implementation being integrated and ready to be demonstrated at the Plumbers conference in two weeks, with Heart expected to be involved and test the implementation before the presentation. The team discussed the coordination between Berkeley alignment and Linux Plumbers, clarifying that ZK Bricks will serve as Berkeley's deployable home with links to their reference code rather than redefining it. Mitchell and Scott engaged in a lighthearted discussion about numerology games involving train numbers and ZK proofs.

### Proof System Technical Discussion

The team discussed technical aspects of proof systems, with Mitchell raising concerns about the current proof only showing membership rather than non-membership, which could be important for integration into OpenVTC. Scott mentioned the round two preview and identified issues with identifier finding WG14 and ED25519 DID key requirements. The discussion included plans for cryptographers to review specific records (007, 009, 022, and 023) and for Glenn's prototype to confirm that MEM-012 is met regarding proof requirements.

### DID Keys Limitations Discussion

The team discussed limitations with DID keys, specifically that they can only hold a single static string and cannot accommodate additional records or evidence after creation. Denys explained that DID peers were introduced as an extension to DID keys to allow for additional information and extra keys, though they don't specify the DADP version. The team also noted the need to review the definition of distinctness in the asynchronous agent context against the PTC's issuance policy. On the 29th, Leif from Syros and the WW wallet team will join the meeting to share real-world insights and benchmarking data.

### PQC Signature Visualization Discussion

The team discussed reviewing Record 23,023 and requested Dennis and other cryptographers to check it out. They planned to have Leif join next Tuesday's meeting to discuss work with the Cirrus team. Mitchell presented a visualization of PQC signatures using a star representation, demonstrating how different signature sizes could be displayed within a trust graph structure. Denys provided context on the size comparison between different PQC signatures, noting that while MDS-44 is the smallest at around 50 times larger than classical signatures, it still provides a lower security level than current standards.

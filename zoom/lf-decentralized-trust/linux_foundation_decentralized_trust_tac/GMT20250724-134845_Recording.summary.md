## Details

### Meeting Attendance and Tracking Discussion

The meeting began with informal greetings and small talk, including Arun discussing his recent marriage and travel in India. Ry and Sean discussed attendance tracking, with Ry preferring to manage it through GitHub for easier querying. Sean confirmed they had a simple majority of the quorum with 6 out of 11 members present, and Arun began the meeting after confirming this with Sean.

### Technical Advisory Council Meeting Updates

The Technical Advisory Council meeting covered several key topics. Arun reminded attendees about antitrust policy compliance and encouraged use of the weekly newsletter for project announcements. Quarterly reports were discussed, with Ramakrishna noting a mix-up in report submissions, which Arun agreed to correct. Wenjing provided an update on a steering committee's progress in developing a report template for a non-coding project. The conversation ended with Kevin presenting a proposal for a new programming language called Compact, which is designed for zero-knowledge proof blockchains and operates using both off-chain and on-chain code with verification through zero-knowledge proofs.

### Impact Virtual Machine Design Overview

Kevin explained the programming model and its components, noting that while he is not an expert in Web3 or blockchain, he can discuss the design considerations for the Impact Virtual Machine (IVM). Matthew inquired about the comparison of the project to other technologies, to which Kevin suggested addressing this question asynchronously. Matthew also asked about the open-sourcing of the IVM, to which Kevin confirmed that everything, including the IVM implementation, will eventually be open-sourced. Kevin clarified that the Compact programming language is agnostic to the blockchain's representation of state updates and that the IVM is designed to support public state updates and provide a cost model for transaction fees.

### Smart Contract Compiler Proposal

The team discussed a proposal for a compact smart contract compiler and SDK, which includes developer tools like formatters and testing infrastructure. Kevin explained that the proposal consists of both a compiler and a specification, with an informal version and a formalization in Agda. Arun asked about the legal components needed for other projects to adopt the specification and SDK, to which Kevin responded that they would need to generate platform-specific code, implement runtime libraries, and handle ZK proof representations.

### Modular Compiler Design for Blockchains

Kevin explained the design of the compiler, which uses a nanopass architecture with multiple intermediate representations and separate backend passes for different target languages. He described how the compiler is designed to be modular, with the backend implementation and runtime library as separate components that could be replaced to target different blockchain ecosystems. Matthew inquired about private data management, and Kevin clarified that this falls outside the scope of the compiler language itself, treating foreign functions as a means to access private data.

### Project Evolution and Community Involvement

The team discussed the evolution of the project, with Kevin explaining that while it currently focuses on the language specification and JavaScript backend, there are plans to support other chains and non-JavaScript backends in the future. He compared this to Python's community-driven feature proposal process and noted that while working on a commercial compiler is challenging, other aspects of the SDK, such as developer tooling, would be more accessible for community involvement. Matthew suggested adding information about the maintainers and team structure to better understand the project's scope and complexity, to which Kevin clarified that the current sponsors are the main implementers and maintainers, while other sponsors are partners with financial relationships but not active maintainers.

### Designing Safe dApp Programming Language

Kevin discussed the design principles of a new programming language for decentralized applications (dApps), emphasizing its familiarity to TypeScript developers while maintaining safety through a strong type system and clear distinctions between private and public data. He explained that the language is intentionally restricted to align with the underlying proof system, lacking features like recursion and unbounded iteration. Kevin also highlighted the potential for community contributions to the developer tooling, which is built to support third-party subcommands, and mentioned the existence of a compiler implementation.

### Zkir and Midnight Language Design

Kevin discussed the Zk proofs representation called Zkir, which is a 0-knowledge intermediate representation specific to Midnight. He emphasized the importance of open language design and introduced the Midnight Improvement Proposal process for proposing new features. Matthew inquired about the peer review of a paper defining foundation private smart contracts, to which Kevin explained it was published in a conference on computer security foundations. Kevin also highlighted the compiler's extensive test suite and outlined areas of focus for targeting other blockchains, while Ramakrishna asked about cross-chain security, which Kevin acknowledged as an interesting but unclear concept.

### Compact Language Feature Development Process

Kevin explained the process for new language features in Compact, similar to Python's PEP process, including community discussions and steering committee approval. He proposed monthly community meetings to share updates and a yearly roadmap for upcoming features. Arun raised questions about cross-chain security and community meetings, which Kevin addressed by clarifying that the compiler currently only knows about the type structure of the ledger, and the implementation would need to be abstracted for different backends. Matthew inquired about ledger data types and was told they are built-in types in the language, with the implementation details to be shared once the repository is open-sourced.

### Project Proposal Review and Access

The meeting focused on reviewing a project proposal presented by Kevin, which was detailed but not yet ready for voting. Arun explained that the project team would respond to questions via GitHub within about a week and a half, after which the proposal could be opened for voting at the next TAC meeting. The team discussed providing TAC members access to the code repository before voting, with Kevin noting that he could request access for specific GitHub IDs but couldn't guarantee it. The conversation ended with a reminder about pending quarterly reports from both TAC members and project teams.

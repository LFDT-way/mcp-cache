## Details

### Trust Council Updates and Deadlines

The October 16th LF Decentralized Trust Technical Advisory Council meeting covered several key announcements and updates. Tracy reminded attendees about antitrust policy and code of conduct requirements, and shared that the Dev Weekly Developer Newsletter accepts submissions, the 2026 TAC term nomination period is open until October 31st, and a workshop on cross-network interop with Hyperledger Cacta is scheduled for November 12th. Tracy also noted that Maintainer's Days registration is open and includes registration for the LFD Team Member Summit on January 28-29. The conversation ended with a discussion of quarterly reports, with some still pending review and others due soon, including the Indy and Anon credits report due today, and the AROHA and Bevel Report next week.

### Bevel Project Status Review

Tracy and Aditya discussed the status of the Bevel project, which had been moved to a dormant state due to missed quarterly reports. Aditya explained that his organization still uses Bevel actively and contributes to it, even though there is no active development. Tracy clarified that to move the project back to incubation, a new proposal would be needed, along with timely quarterly reports. They also discussed the possibility of moving Bevel to a lab as an alternative option.

### Project Review Template Updates

Tracy discussed two PRs related to project reviews and templates. The first PR focuses on making project update templates more generic and applicable to all types of projects, rather than just code projects. It includes instructions for annual reviews, covering topics such as project goals, deliverables, and maintainer diversity. The second PR addresses timing requirements for project updates. Tracy also mentioned an incubation proposal for moving Paladin and Zeto to incubation. Arun briefly mentioned project status, maintenance, and communication expectations.

### Decoupling Lifecycle Changes from Reviews

The TAC members discussed whether annual reviews are the appropriate time to make lifecycle stage changes for projects. Tracy proposed decoupling lifecycle stage changes from annual reviews, noting that while recommendations can be made at any time, actual changes might require more context and consideration. Matthew agreed that while lifecycle changes can be proposed at any time, annual reviews provide a valuable opportunity for in-depth project assessment due to the time and resources available for thorough review. The group acknowledged that while lifecycle stage changes can be separated from annual reviews, the context and depth of analysis provided during these reviews are crucial for making informed decisions about project stages.

### TAC Review Process Clarification

Tracy and Matthew clarified that while the TAC can recommend changes during annual reviews, actual implementation should occur separately through a formal process. Arun raised questions about project metrics and maintenance, suggesting two possible approaches: creating trackable GitHub issues for maintainers to address within 3-6 months, and allowing maintainers to challenge TAC's metrics assessment. Tracy acknowledged that the original process intended for more active involvement from project maintainers in annual review discussions, suggesting a need to improve attendance at these meetings.

### Project Review Process Updates

Tracy and Diane discussed updating the process for project reviews, with Diane suggesting that reports should be presented to the TAC by project members and allowing a week for group review before scheduling a presentation meeting. They agreed on a multi-phase process where submissions would be reviewed by primary and secondary reviewers before recommendations are discussed with maintainers. Tracy mentioned the need to create issues for follow-ups from annual reviews, ensuring ongoing project oversight and appropriate stage changes.

### GitHub Issues for Follow-up Tracking

Tracy proposed using GitHub Issues to track follow-up items from reviews, and Matthew agreed, noting that centralizing action items is better than leaving them in PR comments. Tracy also raised the topic of roadmap files, which are mentioned in project incubation guidelines but not in the common repository structure. Arun questioned whether a roadmap file was a new recommendation, and Tracy suggested consulting with project members about their current practices for roadmap management.

### Project Metrics for Diversity Reporting

Tracy and Diane discussed the need for metrics in project reports, with Diane expressing concern about the lack of required metrics for diversity and participation. Tracy explained that while metrics are not explicitly called out, they are implied in the instructions for TAC members to review contribution activities and diversity of maintainers. Diane suggested adding specific metrics requirements to the report generators' instructions, as she believes it would provide valuable insights into maintainers' perspectives on diversity and participation.

### LFDT Metrics and Diversity Standards

The team discussed the need for generic metrics that can support any type of project in LFDT, emphasizing the importance of metrics that work for both code and standards projects. Tracy and Ramakrishna agreed that while metrics can be misleading, the TAC members should review and assess the accuracy of submitted metrics. They also discussed the project lifecycle governing document, which provides clear numbers for criteria such as maintainer diversity and participating organizations. The team considered changing the terminology to "maintainer-contributor organization diversity" or "participating organization diversity" to better reflect their focus on organizational participation.

### Project Review Process Updates

The team discussed updates to project review processes, focusing on quarterly and annual reviews. They agreed to create a governance repository issue to update the project lifecycle to accommodate different types of projects. The group also reviewed a proposal for timing requirements for project updates, with a suggestion to move projects to a dormant state if updates are not submitted within two months of the scheduled due date. Matthew raised a concern about the feedback loop time, which Tracy agreed to address in the documentation. The team decided to leave the timing requirements proposal open for further review and planned to discuss a project proposal in the next meeting.

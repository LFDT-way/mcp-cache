## Details

### Working Group Output Discussion

The meeting began with a casual discussion about spider webs before transitioning to work-related matters. Matthew introduced the agenda, mentioning two potential outputs from the working group: a new document and updates to existing documentation. He also discussed cleaning up and restructuring a working document to make it more suitable for future PR. Ry brought up a related internal meeting about bug bounties and CBEs for CNCF and another project, which Matthew acknowledged but did not elaborate on.

### GitHub Integration for Bug Bounties

Ry discussed plans to transition away from HackerOne for managing CVEs and bug bounties, aiming to fully integrate these processes with GitHub. He explained that this change would involve moving to a system where bounties are paid through GitHub Sponsors, which offers a more open and consistent payment method. Ry noted that while most LFDT projects currently use HackerOne, some like Bezu and Hiro have separate, well-funded bug bounty programs due to their ability to pay in ETH. The team discussed the need for a consistent approach to handling CVEs across projects, with Ry mentioning that a presentation on these changes would be presented to the TAC in the coming weeks.

### Security Vulnerability Reporting Process

The team discussed the process of reporting security vulnerabilities and creating security advisories in their system. Ry demonstrated how users can report vulnerabilities through a dedicated form, which is only visible to logged-in users. They explored the workflow for handling reported vulnerabilities, including the ability for maintainers to work on issues privately before publishing an advisory. Enrique reminded the group that their discussion was being recorded and published, prompting Ry to pause the recording to ensure they were not sharing sensitive information.

### GitHub Security Documentation Updates

Ry and Matthew discussed the GitHub workflow for handling security issues and the need to update outdated security documentation. Ry explained that the current security.md files need to be revised to reflect recent changes, including moving away from Hyperledger branding and addressing the tension between code delivery and spec delivery projects. They agreed that updating this documentation is a priority, and Ry plans to present a complete proposal to the TAC with a focus on consistency and appropriate guidelines for different types of projects.

### README Standardization Discussion

The team discussed README structure and consistency guidelines for project documentation. Matthew noted that different README formats across projects can lead to varied developer experiences, prompting a need for more consistent meta guidelines. Enrique explained that Firefly's architecture-focused README is appropriate given its complex multi-repo structure, unlike simpler projects with single-repo setups. The team agreed that while README content should be static and point-in-time, the top section could benefit from more stringent guidelines to ensure essential information is easily accessible.

### Project Documentation and Issue Tracking

The group discussed project documentation standards, focusing on README files and issue tracking. They agreed that comprehensive README files with links to scorecards, documentation, and other resources are valuable, though there was some discussion about whether these should be in the main repo or a separate docs repo. The team also discussed issue tracking practices, including the use of labels and prefixes for easier organization and release note generation. Ry shared insights from his experience with Chromium's bug tracking process, highlighting the importance of clear timelines and requirements for addressing issues. The conversation ended with a brief discussion about the need for thorough release notes, with Jessica and Matthew praising the example from Bessu for its completeness and helpfulness for users.

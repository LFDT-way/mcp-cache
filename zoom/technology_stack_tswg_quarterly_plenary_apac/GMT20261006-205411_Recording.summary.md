## Overview

The meeting focused on resolving issues with the TSP (Trusted Source Protocol) specification, specifically discussing the placement of sender identifiers in HPKE (Hybrid Public Key Encryption) and addressing concerns about cryptographic strength. Samuel raised concerns about making the sender identifier field optional in HPKE, arguing that this creates security vulnerabilities and malleability issues, particularly when using longer 32-byte identifiers that cannot be properly hashed to 16 bytes without losing cryptographic strength. Wenjing explained the current implementation using HPKE's base mode with fixed-length tags, but agreed to investigate whether the field could be made optional without compromising security. The discussion also covered the need to clearly define "appraisable" terminology from the Trusted Computing Group specifications, particularly regarding dynamic appraisability for key state verification. Both issues were identified as critical before seeking working group approval of the specification.

## Details

### Document Revision Status Update

The meeting focused on reviewing the status of a document revision and addressing outstanding issues. Wenjing provided an update on the document's progress, noting that it is in revision three and has been successfully tested with implementations by multiple teams including Glenn at Affinity. The group discussed two main topics: the placement of source VID and the term "appraisable" which was previously defined in the Trusted Computing Group specifications but could not be found in the current spec. Wenjing mentioned that the document is ready for the working group to approve, with plans for the steering committee to review it in the coming months to finalize it as version 1.

### HPKE Specification Discussion

Wenjing and Samuel discussed the current version of the HPKE specification, which is now on standard track and uses only the base mode without the informational IFC. Wenjing explained that the base mode has always included features like INFO and AAD for transporting additional information, though these don't provide additional security beyond the ESSR with ECEIS approach. Wenjing demonstrated how HPKE base mode works by showing a TSP message example, explaining that the ciphertext consists of key representations followed by a software text (PAC) containing sender information hashed into a 128-bit tag.

### AEAD Field Security Concerns

Samuel and Wenjing discussed concerns about using a 16-byte AEAD field for sender identifiers, particularly when working with 32-byte hashes. Samuel expressed security concerns about compressing the identifier from 32 bytes to 16 bytes, explaining that this reduces cryptographic strength and could make the system vulnerable to attacks like Grove's algorithm. Wenjing confirmed that the AEAD field is not optional and occupies a fixed 16 bytes, but the discussion ended without reaching a clear resolution on whether to use the field for full-strength cryptographic identifiers.

### Sender Source ID Protocol Discussion

Wenjing explained that the sender source ID is now optional in the protocol design to allow flexibility in using different encryption algorithms, including HPKE. Samuel argued that the ID should never be optional, as relying on encryption algorithms for transmitting the sender source ID could compromise security against impersonation attacks. Samuel expressed concern that making the ID optional complicates the use case without providing significant security benefits.

### HPKE Integration in TSP Protocol

Samuel expressed concerns about incorporating experimental HPKE features into the TSP protocol, arguing that it would corrupt the protocol's simplicity and stability. He recommended using the mature and FIPS-approved sealed box approach instead, with HPKE's core Diffie-Hellman key exchange functionality as the only necessary component. Wenjing acknowledged the concerns but noted the desire to keep both options available, though Samuel clarified he was not opposed to keeping HPKE's basic functionality while avoiding its experimental features.

### HPKE Protocol Design Discussion

Samuel and Wenjing discussed concerns about using HPKE in their protocol, particularly regarding cryptographic strength and protocol design. Samuel expressed strong disagreement with making the sender field optional in HPKE, arguing it over-complicates the protocol and reduces cryptographic security by abbreviating 32-byte IDs to 16-byte tags, which violates cryptographic best practices. They agreed that the sender field should be made required again, and Wenjing will check if the 16-byte tag is mandatory or optional in the current HPKE specification. They also discussed the need to clearly define and reference the concept of "dynamically appraisable" provenance in their documentation, as it's a term of art from the Trusted Computing Group that requires proper specification.

### Dynamic Appraisability Concept Discussion

Wenjing and Samuel discussed the concept of dynamic appraisability, which allows receivers to evaluate the security of a computing environment rather than relying on declarations from senders. They emphasized that this approach avoids the trust-based vulnerabilities present in current systems like PKI, where attackers can exploit certificate authorities. The conversation ended with Wenjing planning to update meeting minutes with two key points for working group approval before proceeding to testing.

## Details

### DID WebS Service Endpoints Discussion

The team discussed service endpoints in the DID WebS specification, focusing on inconsistencies in how URLs are formatted in the current spec. Jonathan identified that some example URLs in the spec were incomplete and needed full paths to be useful. The group clarified that service endpoints are essentially UBI responses, with Samuel explaining that the resolver should return what you would get if resolving a UBI rather than requiring additional UBI resolution steps. The discussion highlighted a philosophical question about whether the DID resolver should do all the legwork to validate service endpoints or provide complete URLs directly in the DID document for user convenience.

### DID Service Endpoint Discussion

Phil explained that the service endpoint definition in the DID document specifies where a mailbox (like BJQ) lives, allowing users to contact it through a URL, even though the mailbox could contain multiple APIs. Samuel clarified that from a security perspective, the DID document serves as a discovery mechanism for other endpoints, including UBI discovery. The group discussed whether to include an optional attribute in service endpoint sections to reference target DID documents, with Jonathan noting that this would be unprecedented in DID core and potentially useful for supporting chaining in future versions.

### DID Document Specification Discrepancies

The team discussed discrepancies between the DID document specification and the current reference implementation regarding the "also known as" section. Jonathan identified that the DID Carry specification requires listing the DID Carry identifier, though the specification needs updating to reflect current practices. The group also discussed whether including a DID Web identifier in the also known as section was redundant, with Jonathan expressing concern about including the DID subject in this section. Kent suggested the current implementation might contain imprecise language that needs clarification.

### DID Web Implementation Bug Fix

The team identified a bug in the reference implementation where redundant DID Web S and DID Web identifiers were included due to cut and paste code. Jonathan confirmed this was an easy fix and the group agreed to clean up the URLs and language in these sections before presenting for voting at the next DID WebEx meeting in a month. Daniel provided a status update on open PRs for the dossier spec, including conceptual additions comparing verifiable presentations and addressing lifecycle differences between evidence types, and requested review of the joint issuance mechanism section which he acknowledged needed improvement.

### FHIR Patient Data Dossier Structure

Phil discussed using a dossier to capture FHIR resources representing a patient's lifetime data, and sought advice on how to structure this approach. Daniel explained that not all data formats lend themselves to certification, suggesting that for non-certifiable data like DICOM images, hashing the content might be simpler than embedding it in a certified document. Samuel added context about the original motivation for SEDS and the challenges of cryptographic agility, explaining how externalizing digests can reintroduce identification problems unless handled properly through wrapper conventions.

### Data Canonicalization Standards Discussion

The team discussed implementing a convention for describing uncertifiable external data using ACDC wrappers with a specific field for data digests. Carly shared that her team is using DCAT standards and JSON canonicalization schemes to handle external resources and maintain data order. The group identified a gap in FHIR's canonicalization specifications and discussed adding URN SED support to the Caesar spec rather than modifying the IONIS spec, with Samuel confirming this approach would be compatible with cryptographic agility requirements.

### Capital M Threshold Operator Discussion

Daniel presented section 11 of the specification regarding joint issuance, which defines a capital M threshold operator for requiring a minimum number of signatures. Samuel questioned the need for both M and MGRP fields, suggesting that a pure threshold operator without additional information might be simpler. The group discussed whether to use edges for all potential signers or just actual signers, with Daniel explaining the need to qualify possible signers in some cases. Daniel invited feedback on the section and acknowledged that different approaches could be valid, depending on the specific use case.

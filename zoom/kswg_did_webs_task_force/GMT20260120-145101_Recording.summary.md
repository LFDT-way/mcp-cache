## Overview

The team reviewed and discussed updates to the Dossier specification, focusing on joint issuance logic and the implementation of M-group and Q-group operators in a graph database. They explored concepts around potential and actual signers in governance frameworks, including threshold definitions and the role of ecosystem governance in managing ACDCs. The conversation ended with discussions about DID Web security implications, trust verification processes, and plans for future specification reviews and updates.

## Details

### Joint Issuance Logic Specification Updates

The group discussed the Dossier specification and joint issuance logic. Daniel presented his work on formalizing joint issuance patterns, including leader-follower strategies and M-group operators. Samuel suggested adding an arity field to edge groups to simplify the representation of M-group operators. The group also discussed the concept of Q-group operators for qualifying signers, though this would require extending the current specification. Daniel agreed to revise the specification to allow for these new operators and fields.

### Graph Database Operator Implementation

The team discussed the implementation of M-group and Q-group operators in a graph database. They clarified that the arity of an operator should be stored in a separate field next to the operator, rather than in the operator field itself. Samuel explained that ACDC edge groups have an O field reserved for M-area operators, and each edge can have multiple unary operators. Daniel and Samuel discussed how to express qualifications for queue groups, with Daniel explaining that the schema specifies requirements for signers, such as having a VLEI edge or an entitlement from a voting authority. Kent asked about defining schemas for edges or groups, and Daniel clarified that the qualification applies to edges that are added to the edge group, not to the edges themselves. Samuel suggested simplifying the terminology by referring to these operators as "arity operators" rather than "group operators."

### ACDC Semantics and Governance Framework

Daniel and Samuel discussed the distinction between potential and actual signers in a governance framework, focusing on threshold concepts and the complexity of semantics in ACDCs (Access Control Decision Contexts). Samuel explained the difference between M-of-N thresholds and absolute thresholds, emphasizing that real-world applications often require additional semantics beyond what can be contained in ACDCs themselves. They agreed that an ecosystem governance framework should provide the context and additional semantics, allowing ACDCs to remain more focused and manageable.

### Ecosystem Governance and Signer Framework

The team discussed ecosystem governance frameworks and how to identify potential signers for ACDCs. Samuel suggested using attributes to store potential signer IDs, which Daniel agreed was a good approach. They also reviewed some open items from a previous meeting, including reviewing definitions with Hank, updating the spec to use gray highlighting for informative versus normative content, and making changes to the spec and implementation to clarify the role of DID Web.

### DID Web Specification Updates

The team discussed changes to the DID Web specification, focusing on the relationship between DIDWEBS and DID Web DIDs. Samuel explained that a DID Web DID should only be trusted if accompanied by an ACDC in the Caesar stream, and Kent agreed to create an issue to update the specification accordingly. Jonathan noted that the specification is now feature complete, with only minor polishing needed before formal review. Kent also mentioned that their pull request to the W3C test suite has been merged, and the team is working on the diff-recommended status.

### Conditional Proof 2022 Status Review

Jonathan and Kent discussed the status of conditional proof 2022 being formally listed as a did method extension and the need to schedule a second deep dive with the DIF ted Methods Working Group. They aimed to have the DIF recommended status resolved before the Caricomp in April. Samuel suggested adding language to highlight the security feature of revoking a didweb did in case of a DNS hijack, which Kent agreed to include in the spec.

### DIDWEB Trust and Specification Review

The group discussed the handling of DIDWEBs in the context of DID documents and trust. Jonathan emphasized that the absence of a DIDWEB in the "also known as" array should be treated as an explicit choice not to trust it, and Kent noted this would require updates to the reference implementation. The team agreed to conduct a final review of the specification in the coming weeks to clarify language and address outdated content. Phil raised concerns about the potential vulnerability of trusting DIDWEBs, which Jonathan acknowledged, though he noted that the current approach assumes trust only if the DIDWEB is explicitly listed.

### DID Web S Security Concerns

The group discussed the security implications of DID Web S, particularly focusing on the role of trusted resolvers in verifying Cal documents. They agreed that without a trusted resolver, there are no security guarantees, as untrusted resolvers could modify or hack DID documents. Kent mentioned that they need to schedule a second deep dive with the Diff Did Methods Working Group and get Conditional Proof 2022 formally listed as a did method extension. The conversation ended with Ed discussing a browser extension he is building that would allow users to trust websites by verifying their authenticity through signed credentials or DID Web S.

### Security Vulnerability Reporting Process

Enrique and Alexei discussed the process for handling security vulnerabilities in their project. They reviewed the documentation and identified that they need to ensure the security reporting process is clearly outlined and accessible. Enrique suggested tagging Firefly maintainers on Discord to gather more project maintainers, emphasizing the importance of diversity in the security team. They also discussed the need to make the vulnerability reporting process more prominent in their documentation and confirmed that security reports should be sent to the community architects' email list.

### GitHub Security Management Strategy

Enrique and Alexei discussed the process of reporting security vulnerabilities through GitHub, focusing on the security tab and the visibility of reported issues. They considered transitioning all repositories into a single GitHub organization for better management and discussed the potential creation of a dedicated repo for security policies. Enrique planned to tag people on Discord to encourage participation in the security team and to follow up on who wants to join. They also debated whether security advisors should be limited to the main Firefly repo or spread across different repositories, considering the varying frameworks and technologies used.

### Firefly Security Team Discussion

Enrique discussed amending a previous point about security vulnerabilities and emphasized that they should be reported at the specific repository level for each component. He clarified the correct spelling of the project name as "Firefly" with a second "Fs" and capitalization. Enrique also mentioned adding this to the agenda details and discussed the need to raise a Discord thread to tag Firefly maintainers for building a security team. Simon briefly mentioned the security MD contents and scorecards, but the transcript ended before further details were provided.

### Cardano Scorecard Implementation Discussion

Simon and Enrique discussed the implementation of scorecards for the Cardano repository. Enrique explained that while scorecards are beneficial, they are not mandatory for all repositories. He clarified that the current scorecard system measures metrics like security and code quality on the main repository. Simon expressed interest in ensuring there was no outstanding work for the Cardano repo. Enrique mentioned that he would raise the question of whether scorecard reports can be aggregated across multiple repositories in the Tac group. They also discussed the 80% score figure, which Enrique believed might be related to contributor activity. Simon noted the importance of being informed of any surprises regarding the scorecard.

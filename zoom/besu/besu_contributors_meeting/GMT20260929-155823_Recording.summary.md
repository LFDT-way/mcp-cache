## Details

### GraphQL API Feedback Discussion

Justin opened the September Besu Community Contributor Call and discussed two main agenda items. He announced plans to gather feedback on the GraphQL API, explaining that while it has potential cost savings, it's not well-specified and creates technical debt. Justin requested input from users about the API's utility and usage compared to the RPC/JSON RPC API, noting that deprecation is being considered but would not happen immediately without strong justification from users.

### GraphQL and Tracing API Standards

The group discussed the GraphQL remote RPC interface for Besu, with Matthew and Ghan agreeing that it's rarely used compared to standard JSON-RPC interfaces. Ghan explained that enterprises might prefer security layers like Envoy over GraphQL capabilities, and noted that GraphQL creates a design mismatch for Ethereum by tying developers to a specific interface. Justin then introduced a proposal to standardize tracing APIs, particularly important for L2s and ZK L2s, and invited community members to participate in forming opinions and working groups for this initiative.

### Tracing Standards Working Group Discussion

Justin and Gary discussed a working group focused on creating consensus around tracing standards across execution clients, with Gary suggesting the outcome should be an EIP with a champion to guide it through the process. Justin updated the meeting agenda with a link to shared materials and agreed to send it directly to Gary. Edward from Hashgraph (formerly Swirled Labs) introduced himself and prepared to present Clipper, noting the confusion around the company's name changes and asking if anyone in the audience was familiar with Clipper.

### Clipper Interledger Protocol Presentation

Edward presented Clipper, an Interledger protocol recently transferred from Hedera to the LFDT, explaining its architecture and design principles. He outlined different approaches to interledger communication, including oracle-based solutions, light clients, and native integrations, positioning Clipper as a hybrid approach between light clients and native integrations. Edward emphasized that Clipper is a messaging protocol focused on data transfer between ledgers, preserving ABFT semantics, and aims to inspire native integration by providing a scalable and modular standard.

### Clipper Endpoints Architecture Discussion

Justin asked how the Clipper endpoints, which appear similar to bridges, are not just reinventing a bridge. Edward explained that while these endpoints may seem like a bridge, they operate using a light client model where trust is in the state proof rather than the relay itself. The Clipper endpoints monitor source chain state, construct state proofs, and exchange bundles with each other, with the trust being in the implementation of the verifier contracts that validate these state proofs.

### Clipper Cross-Ledger Transaction Handling

Edward explained Clipper's handling of cross-ledger transactions, describing a single-threaded execution model where messages are processed in first-come, first-serve order with a running hash to maintain order and validate message sequences. Gary questioned whether this sequential processing could create bottlenecks if transactions fail to execute due to censorship or high contention, and Edward confirmed this would be the case, with throttles and communication channels used to manage message flow between ledgers.

### Cross-Ledger Transaction Inclusion Guarantees

Gary discussed inclusion guarantees for cross-ledger transactions, highlighting the challenges with Ethereum's 12-second block time variability and the need for time-bound guarantees. Edward explained that Clipper's asynchronous messaging protocol has eventual processing but no guaranteed timeframes, while Ethereum's system has similar issues with no firm inclusion guarantees. Matthew inquired about the application of this technology in permissioned versus public blockchain environments, questioning its suitability for different types of ledger systems.

### Hashgraph HARO Network Integration

Edward presented Hashgraph's HARO networks, which facilitate interledger communication between different blockchain networks including Besu and HiRO. He explained the technical architecture including Clipper endpoints, verifier contracts, and connector entities that enable cross-ledger communication. The discussion included a live demonstration of a round-trip transaction between Besu and HiRO networks. Edward expressed interest in potentially implementing a native Clipper solution for Besu, which Gary suggested could be explored as a plugin implementation.

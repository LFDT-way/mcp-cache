### RC1 Release Candidate Updates

Joseph explained that the release from RC0 to RC1 included three main changes: a more robust SHA-256 implementation search in the compiler, updating Ledger dependencies to version 9.1 RC3, and fixing field ordering in shielded receive events to ensure correct indexing. Kent noted that RC0 was already feature complete, with later release candidates addressing bugs and stabilizing the release for shipping. The team discussed the timeline for Midnight Foundation's review, expressing a desire to align their work with consumer needs and facilitate a smoother transition.

Jonathan discussed his work on the PR for the Compact Reference Manual, focusing on adding material about contract types and cross-contract calls. Joseph explained the release process, which involves using the Midnight Docs repository and GitHub Actions to automatically create and deploy PRs to the public docs website. Kent and Jonathan raised concerns about releasing updates that might not be suitable for mainnet or pre-prod environments, highlighting the need for careful consideration of the hard fork mechanism and documentation updates, including SECP support and casting semantics.

Jonathan mentioned that COIP2 is still not officially accepted, pending one final PR that involves using contract types instead of interfaces. The team agreed they need to decide whether to proceed with documentation updates before potentially changing the behavior.

### COIP Process and Planning Discussion

The team discussed merging a PR and following the process to make it an accepted COIP, with plans to address this next week when Kevin is available. Jonathan proposed starting a new draft COIP for the next phase of work involving dynamic code discovery, including writing the rationale even though the specification isn't complete yet. Joseph suggested creating separate COIPs for each restriction including dynamic discovery and witnesses, with the team agreeing to have all proposed approaches and problem statements finalized before the private state architecture workshop at the end of July.

### Private State Architecture Management

The team discussed the management of private state architecture, with Kent expressing concern that current implementation leaves too much responsibility with dApps rather than the core system. Jonathan emphasized that the trusted component should be the private state manager, similar to how wallets handle secret keys. Joseph noted that MidnightJS is currently agnostic about where private state is stored, offering browser storage defaults but could easily be adapted to fetch from wallets, and the discussion highlighted the need to determine where private data is stored and how it should be managed across different components.

### Private State and Witnesses Model

The team discussed the relationship between private state and witnesses in contract implementations. Joseph raised questions about initializing private state when calling contracts without prior code knowledge, particularly when witnesses are involved. Jonathan explained a proposed three-level model where witnesses sit between contracts and DAPs, with multiple witness implementations and private state models possible for a single contract type, while different DAPs can work with the same private state model.

### Witness Sub-language Contract Discussion

Joseph and Jonathan discussed the potential for creating a sub-language for witnesses in contracts, particularly for functions built on the same primitives as DAO contracts. Jonathan explained that from a mathematical model perspective, the private state machine needs to have well-defined, reversible functions to ensure the product state machine remains deterministic. The group agreed to surface proposals and follow-up quotes in the coming weeks.

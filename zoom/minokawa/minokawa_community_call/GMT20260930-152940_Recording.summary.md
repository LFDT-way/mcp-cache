## Details

### Compact Compiler Multi-Target Proposal

Parisa led a meeting discussing Compact 0.35 release and its compatibility with pre-production environments, confirming it targets Ledger 8 with staging network on Ledger 9. The main discussion centered on a proposal for multi-target Compact compiler, where Parisa suggested releasing multiple binaries rather than implementing target selection flags. The proposal includes predefined target combinations of ZKAR and unchained runtime, with the compact dev tool automatically selecting the appropriate binary based on the network specified. An open question remained about whether multiple ZKAR versions should be provided for a single target to ease development burden, though Parisa noted mixed opinions on the importance for end users.

### Multiple ZKIR Version Support Implementation

The team discussed implementing support for multiple ZKIR versions within a fixed set of combinations using the compact tool. Kent proposed allowing users to select different Compact C binaries through flags, with each release containing different binaries to support various network combinations. The group agreed to record compiler and ZKIR versions in the manifest (contract.json) for future reference and rebuild capabilities. They voted to assign this feature the number 5, and the conversation ended with Parisa beginning to discuss an old PR regarding constructor operations.

### Contract Constructor Operation Restrictions

Parisa discussed restrictions needed for operations within contract constructors, specifically questioning whether certain operations like balance and time-related functions should be blocked. Joseph explained that while these restrictions aren't explicitly documented, they are determined by ledger semantics during deployment, suggesting they should review the ledger code rather than create new rules. The team agreed to examine the ledger code to determine precise validation rules, and Joseph confirmed that cross-contract calls remain restricted in constructors.

### COIPs and AI Code Process

The team discussed processes for handling COIPs (Community-Oriented Improvement Proposals) and AI-generated code submissions. Kevin explained that the current process requires either rejecting proposals outright or assigning them numbers to allow authors to work on them while the community reviews them. The team agreed to put two pending COIPs on the agenda for next week's discussion after TSC members review them. Kent raised concerns about accepting AI-generated PRs, arguing that once AI-generated code is accepted, the project becomes dependent on AI for maintenance, and suggested considering a wholesale switch to Rust backend instead of maintaining multiple language implementations. The discussion also touched on the need for clear motivation and partnership with Midnight Foundation to prioritize COIPs, as the current limited capacity means many proposals sit in backlog.

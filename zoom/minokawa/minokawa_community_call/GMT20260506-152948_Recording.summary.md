## Details

### Compact Release 1.0 Planning Meeting

The team discussed the next release of Compact, potentially version 1.0, with planned features including Jubjub Scaler and pipe system changes, as well as Schnoor signatures. They determined that based on their typical 4-week release schedule, the next release would be on May 27th, with branching occurring the week prior on May 20th.

### JavaScript Reserved Words Discussion

Parisa and Kent discussed reserved words in JavaScript, specifically addressing issues with identifiers that are not allowed in JavaScript but were being accepted in their system. They identified problems with allowing eval and arguments as names for circuits, as these are reserved in some JavaScript versions. Joseph volunteered to take responsibility for the snore signatures to ensure they are properly implemented before the release.

### Signature Checking Implementation Planning

The team discussed signature checking implementation, which Jonathan identified as needed within the next 6 weeks, though Kent clarified this would be post-1.0 rather than part of the initial 1.0 release. Kent explained that the key focus for 1.0 would be implementing braking changes, followed by a deprecation process and compatibility story. The discussion highlighted potential concerns about type system changes for JubJobscaler, particularly regarding subtyping rules and the requirement that casts between Uints and fields cannot be omitted, though Kent mentioned plans to provide a fix-up tool for affected code.

### Compact 1.0 Signature Implementation Planning

The team discussed the relationship between Compact 1.0 and other signing implementations, with Joseph explaining that RSA and ECDSA signatures would be added after merging SECP256K1 and BIGUInt data types, which are planned for Q2. Kent confirmed these changes are the highest priority items and emphasized they won't wait until the end of Q2 to deliver on signatures. Kent also mentioned working on a proposal for backward compatibility that would include version numbers for library imports, modules, and a syntactic flag to specify parser versions.

### Version Number Implementation Discussion

Kent discussed implementing import version numbers and a parser flag before the 1.0 release, potentially replacing or reducing the need for Pragma. Jonathan suggested using version numbers similar to those in Pragma for imports. Parisa raised the topic of package update guidelines, specifically regarding security risks, and sought the team's input on whether updates should be immediate or more selective.

### Rust Package Update Policy Discussion

The team discussed concerns about package updates in their Rust-based system, with Kent expressing preference for a stable version model where only security and bug fixes are applied. Parisa confirmed they can configure Dependabot to only generate pull requests for security vulnerabilities, and the team agreed to implement a longer cool-down period for updates, with security fixes being processed immediately but still requiring review. The team also discussed expanding the rotation of team members handling package updates to include Jonathan, Casey, and the QA team, and Parisa mentioned welcoming new QA team members including Matthew, William, and Galbi, offering to provide guidance on the QA process.

### Testing Repository Structure Discussion

The team discussed the different types of tests in the repository, including unit tests in test.ss and end-to-end QA tests. Kent explained the policy of keeping these tests separate to prevent the propagation of misconceptions. Matthew and Will are working on understanding and building a coverage matrix for all the tests. The group agreed that a separate meeting or tour would be more appropriate to address specific questions about the testing structure.

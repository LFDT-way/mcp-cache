### Strongly Typed Contract Implementation Discussion

The team discussed Kevin's proposal to introduce strongly typed curve points and field types into the generated JavaScript for contracts. Joseph presented the idea of implementing these operations in the on-chain runtime, but Thomas expressed concerns about the trade-offs and suggested it might be more appropriate to place these operations in the compact runtime library. The discussion highlighted the need to consider the best location for implementing such functionality, balancing convenience with proper abstraction and separation of concerns.

### Cryptographic Implementation Strategy Discussion

The team discussed implementing cryptographic functionality, with Andrzej highlighting challenges around using WASM modules, including cross-technology boundaries and iOS compatibility issues. Thomas questioned whether a WASM module was necessary given the use of standard curves, suggesting off-the-shelf JavaScript libraries might be sufficient. The discussion also touched on the possibility of using the ZK IR v3 package as an alternative approach.

### ZKIR WASM Libraries Evolution Discussion

Joseph and Thomas discussed the evolution of ZKIR WASM libraries potentially becoming a replacement for the on-chain runtime, particularly if they proceed with composable contracts. They acknowledged that while this is not the current state, it might be reasonable to invest in exposing it in the on-chain runtime as a short-term solution before implementing a better long-term solution. They also noted that eventually zkIRv3 will need to depend on the on-chain runtime package for executing impact code.

### ZK-IRV3 Implementation Timeline Discussion

The team discussed the timing and requirements for releasing new curve functions, which are tied to ZK-IRV3 implementation. Thomas explained that while the functions could be added to Ledger 8.2, there isn't enough organizational bandwidth or demand to justify cutting a new release at this time. Kevin clarified that ZK-IRV3 will require a version bump to 3.0 due to new operations being added, and the team needs ZK-IRV3 to stabilize before considering a Ledger 8.2 release. The discussion concluded with an estimate that implementing the necessary changes could take a week or a few days, but the main challenge would be coordinating updates across all systems.

### ZKRv3 Implementation Status Discussion

The team discussed the status of ZKRv3 implementation and Ledger versions. Thomas clarified that Ledger 9 is moving to preview while Ledger 8 remains the primary version until mainnet switches, and ZKRv3 features are currently disabled by default in Ledger 8 but will be available in Ledger 9. Kevin explained that their team needs specific ZKRv3 components for key generation binaries and WASM packages, with a current workaround using two separate binaries that the compiler dispatches between. The team agreed that while there is shared code, they need to maintain separate implementations to precisely replicate old behavior.

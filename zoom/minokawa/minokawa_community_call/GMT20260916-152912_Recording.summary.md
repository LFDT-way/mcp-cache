## Overview

The meeting focused on the multi-environment COIP and how to handle different ledgers and dependencies in the Compact compiler and tooling. Parisa explained the current proposal to add a ledger flag and discussed whether the compiler should have a default ledger, with Kevin and others arguing that the compiler should require explicit flags and that DevTools should provide the default network experience. The group discussed whether the standard library is independent of ledger, on-chain runtime, and ZKIR, and concluded that it depends on both on-chain runtime and ZKIR. They considered whether contractmanifest.json should record ZKIR and on-chain runtime versions, and how documentation should reflect these dependencies. Joseph and Kevin suggested that the compiler should be configured by direct dependencies like on-chain runtime and ZKIR versions, with a higher-level tool managing compatibility and network targets. Yurii and Kent proposed a “target” model similar to machine types in other compilers, with multiple builds of Compact-C each specialized for a supported combination of on-chain runtime, ledger, and ZKIR, rather than a single build supporting all options. The discussion also touched on versioning the standard library, the potential need for different formatter and fixup tool versions, and the challenge of supporting custom networks. The conversation ended with general agreement to focus the COIP on desired user experience and the target-based approach.

## Details

### COIP Public Events Implementation Review

Parisa led a meeting and discussed the public events COIP implementation, which has been completed. She planned to edit the document based on the implementation changes and have TSC review it for tracking purposes. No objections were raised to this plan.

### Multi-Environment COIP Ledger Solution

The team discussed implementing a multi-environment COIP solution to address different networks using different ledgers while the compact compiler only supports a single ledger. Parisa presented a proposal to introduce a ledger flag mechanism that would allow users to choose a ledger version, with the option to use a default ledger or require explicit specification. Kevin suggested that the design should consider the user experience provided by DevTools, proposing that the compiler could be invoked without a default ledger if DevTools handles the appropriate flag selection.

### Ledger Independence in Compiler Configuration

Parisa discussed the default network configuration and ledger independence in the compiler. The group clarified that the standard library is not fully ledger-independent as it depends on ZKAR, which varies by ledger. Joseph suggested an alternative approach using on-chain runtime version flags instead of ledger flags, with a separate tool to handle compatibility matrix and set appropriate flags based on the network environment.

### Compiler Configuration and Dependencies

Kevin and Parisa discussed the configuration of a compiler based on direct dependencies, with Joe suggesting a specific implementation approach. Parisa expressed concerns about user-friendliness, particularly for average users who may not understand technical concepts like "unchained runtime." The discussion focused on whether the compiler should have flags for both unchained runtime and ZKR, with Kevin noting that some combinations would not work. Parisa clarified that unchained runtime is not independent of ZKR.

### ZKIR and Runtime Dependency Discussion

The team discussed the dependency of a standard on both ZKIR and on-chain runtime components. Kevin clarified that adding a new native to the standard library requires both JavaScript implementation in the compact runtime and ZKIR support, making it dependent on both systems rather than independent of them. The discussion then shifted to examining the current ZKAR V3 library components, including a key generation binary and WASM code, before ending with a question about whether contractmanifest.json should record ZKIR version information.

### Documentation Versioning Strategy Discussion

The team discussed recording ZKIR and on-chain runtime version information in documentation. Parisa expressed concerns about revealing unchained runtime and ZKIR versions in docs, particularly for ledger ADTs generated by the compiler. Joseph suggested creating diagrams to understand the versioning system better and proposed that different docs might be needed for different networks and compiler versions. Kevin raised the question of whether the standard library should be versioned, noting it becomes more complex when making breaking changes.

### Standard Library Versioning Discussion

The team discussed versioning the standard library and associated tools. Kevin explained the vision for different network environments similar to Cardano, with regular promotions from preview to pre-prod to mainnet. The group debated whether formatters and fix-up tools should be versioned separately or treated as independent packages, with Parisa ultimately deciding to consider this out of scope for the current proposal. Parisa also raised concerns about potential dependencies on on-chain runtime or ZKR changes, suggesting either proactive consideration of these dependencies or being prepared to address them later.

### Backend Version Management Strategy

The team discussed the challenge of managing multiple backend versions of Midnight Natives and Midnight Ledger, particularly due to dependencies on on-chain runtimes. Kevin suggested considering the user experience of selecting different ledger versions when releasing new versions like Ledger 11, which might change underlying native fields. Yurii proposed creating a new target flag system to handle different combinations of ZK and ledger versions, similar to how compilers handle target specifications for different platforms.

### User Experience and Update Strategy

The team discussed the need to decide on the user experience and agreed that the compact updater should be the primary focus rather than the on-chain runtime. Kent suggested using a machine-type flag approach similar to what worked in the Shay scheme, where combinations of operating system and architecture determine the backend configuration. Kevin supported this approach, noting that the compiler could either use conditional code with flags or have separate binaries for different network configurations.

### Compact-C Version Management Approach

Kent and Parisa discussed the approach for managing different versions of Compact-C and the Compact Updater tool. Kent proposed using multiple specialized builds of Compact-C rather than a single version that supports everything, with the updater selecting appropriate builds based on configuration and target requirements. While this approach would provide a good user experience, it would also allow for more targeted development and avoid the complexity of a single build supporting multiple scenarios. Parisa agreed to explore this multiple builds approach as a better solution to their current challenges.

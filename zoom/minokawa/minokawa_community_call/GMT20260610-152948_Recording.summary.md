## Details

### Security Bug Reporting Procedures

The team discussed a security bug report that was submitted to the wrong repository for Compact 0.31. Kent explained that the report was actually legitimate, involving a missing check in common subexpression elimination that could allow unsafe casts to be turned into safe casts. The team confirmed that Chris Ferry had already enabled private security reporting functionality on GitHub, though initially there was confusion about whether it was properly enabled. Joseph suggested adding automated checks to prevent public reporting of security issues, while the team noted they would need to be attentive when reviewing new issues to ensure proper security reporting procedures are followed.

### Event Logging Implementation Discussion

Kent and Jonathan discussed the implementation of event logging using Memphora Events, with a focus on the syntax and functionality of the "emit" keyword and related functions. They decided on the syntax for "emit," which takes a single argument as an expression and requires it to have one of the enumerated exception types. Additionally, they implemented CRLIs and DCRLIs as standard library functions with generic type parameters for serialization and deserialization processes.

### Serialization Functions Discussion

The team discussed the necessity of serialize and deserialize functions in their system. Kent explained that these functions are useful for handling miscellaneous exception types and packaging arbitrary compact values, though they would result in two serialization steps when emitting miscellaneous events. Joseph questioned whether these functions would be needed if the system eventually supports arbitrary event messages, suggesting that serialization could be handled behind the scenes without exposing it in the source language. The discussion highlighted a potential asymmetry between emit as a keyword with magic type behavior versus serialize/deserialize as standard library functions, with Kent noting that while the standard library functions are innocuous, the keyword nature of emit creates limitations for other uses.

### EMIT Keyword vs Library Discussion

The team discussed whether to make "emit" a standard library routine or keep it as a keyword. Joseph argued that "emit" would likely be used frequently for debugging purposes, while Kent and Jonathan agreed that reserving the word would be appropriate due to its expected frequent use. The group also touched on the need for serialization and deserialization functionality, with Kent suggesting these might eventually be implemented as VM instructions rather than compiler-generated expansions.

### System Implementation and Privacy Updates

The team discussed issues with a clunky size type parameter in their current implementation, agreeing to leave it as is for now. They debated whether to keep the serialize and deserialize functions after Q2, with Kent expressing support for them as they align with Inigo's preference to avoid casts between cryptographic values except through bytes objects. Jonathan provided an update on the COIP for interfaces and cross-contract calls, noting that test cases generated by Bob with AI assistance identified features that wouldn't be delivered soon, particularly those involving private cross-contract calls and state. The discussion concluded with confirmation that privacy-focused token contracts using ZK proofs are feasible in their system.

### Semaphore Protocol and Privacy Enhancements

Joseph discussed the Semaphore protocol implemented on Ethereum, which includes privacy-preserving inclusion and exclusion sets, and mentioned a previous project called Moneta that aimed to create a private stablecoin. Jonathan expressed interest in this area and noted that current cross-contract test cases were overly focused on fully privacy-preserving functionality, which limited their relevance. Jonathan decided to revise the test cases to include more practical applications, including a public DEX that could be implemented with the current quarter's deliverables.

### Toy Demo Test Strategy Discussion

The team discussed focusing on small toy examples and casting a wide net on test cases to create a demo by the end of Q2. Jonathan suggested creating a catalog of test cases, including both expected passing and failing cases, to store in the COIP repository's subdirectory as supporting material. Tracy, a security engineer from CertiK, inquired about the project's compiler correctness strategy, particularly regarding how generated circuits and runtime artifacts preserve source-level semantics. Kent explained that while formal verification is aspirational at this point, the team relies on heavy testing and is working through IO groups to develop a formal definition of ZKR and verify compiler correctness.

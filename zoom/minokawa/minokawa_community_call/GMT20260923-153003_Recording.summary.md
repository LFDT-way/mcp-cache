### Dynamic Dispatching Proposal Discussion

Jonathan presented a proposal for dynamic dispatching in cross-contract calls, explaining how the current Compact release restricts code execution to a single version for contract types. He outlined the goal to transition from type-based to value-based determination of code execution, allowing different code to run depending on the specific contract value passed. The current system uses a fixed import path for contract code, which limits flexibility in application structure.

### Contract Resolution System Redesign

Jonathan and Joseph discussed the rejection of a proposed registry system for finding and running deployed contract code due to concerns about standardized contract representation and security. They explained that instead of providing a fixed solution, they are delivering mechanisms for DApps to handle contract code resolution through a module type in TypeScript and a contract module provider with a resolve method. The new approach gives DApps flexibility in how they resolve contract addresses to code, allowing them to choose between locked-down and trusting approaches.

### Midnight JS Contract Module Implementation

Jonathan explained that Midnight JS includes a simple contract module provider that uses a static map from contract addresses to module thunks, as well as a more sophisticated dynamic lookup system developed by the QA team. He detailed various error cases that could occur, including missing providers, compilation mismatches, and verification key discrepancies. The new implementation allows for dynamic dispatch similar to Ethereum DEXs, though the app must handle the dispatch mechanism itself.

### Cross-Contract Calls and ZK Proofs

The team discussed the implementation of cross-contract calls and zero-knowledge proofs in the new system. Jonathan and Joseph clarified that no on-chain changes were made, and the syntax of compact language remains unchanged, though semantics have evolved. Yurii inquired about the ZKAR backend and TypeScript backend, and Kent explained that while the zero-knowledge proof code handles branches differently than imperative code, the logic follows the same pattern as JavaScript code, with cross-contract calls being guarded to match the behavior of the original code.

### Three-State Outcomes in Cross-Contract Calls

The team discussed handling three-state outcomes (true, false, and failure) in cross-contract calls, particularly regarding ZKAR proof circuits. Joseph clarified that while failures in rehearsal can be detected and handled, proof failures cannot be caught and processed within the calling contract, as the proof mechanism works differently from standard conditional logic. Kent explained that while proof execution should succeed if the rehearsal is correct, transcript application can still fail on-chain, making it impossible to catch all potential failures within the calling contract's code.

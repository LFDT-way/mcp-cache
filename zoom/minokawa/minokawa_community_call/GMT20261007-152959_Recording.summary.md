Iskander explained that the current transient hash implementation cuts the last eight bits, making it unsuitable for their use case of hiding values of type Field. Kent suggested creating a midnight problem statement for this issue, which would involve the crypto team developing a more suitable hash function that doesn't truncate bits. The discussion also touched on the need to generalize elliptic curve operations in the API to allow future curve changes without breaking modules, though Kevin clarified that while generic curves are possible, the current system uses overloading rather than true generics.

### Hash Consistency and Serialization Issues

The team discussed concerns about persistent hash consistency when default curves change. Jonathan and Kevin clarified that Compact does not have a concept of default curves, requiring explicit curve identification for each operation, which should address Iskander's initial concerns. The discussion then shifted to serialization format and consistency issues, with Parisa proposing to modify the compiler to ensure serialization follows the same descriptor path as other operations.

### System Serialization Format Standardization

The team discussed standardizing serialization formats across different components of the system, including serialized/deserialized circuits, events, and chain information. Kevin emphasized the need to first define a clear serialization format before making any implementation changes, and proposed adding version bytes to ensure backward compatibility. The group agreed that descriptors and flattened data types should align with each other, and Kevin committed to drafting a proposal within a couple of weeks that would specify the format details and address inconsistencies between current implementations. The team also discussed the relationship between serialization and hashing functions, particularly regarding persistent hash requirements, and agreed to stage the work to focus on specification before making implementation changes.

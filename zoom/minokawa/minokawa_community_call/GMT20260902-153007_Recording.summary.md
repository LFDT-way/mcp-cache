### AI Policy and Authorship Guidelines

The team discussed AI policy and authorship guidelines, with Kent clarifying that shielded employees should attribute authorship to Midnight Foundation rather than personally, though personal copyright is not required to be given up. Kevin proposed moving internal language discussions from Slack to Discord to increase open source engagement, suggesting they archive their current internal Slack channel and transition discussions to Discord, particularly using the LFDT Discord server.

### FAB Engagement and Standardization Discussion

The team discussed the need to better engage with the compact team and standardize FAB. Kevin suggested creating a dedicated space for discussions, similar to how Google handled open source projects. Parisa agreed to share a Discord link, though she noted finding an accurate one was challenging due to historical naming issues. Yurii requested the definition of co-authorship policies in ContributionMD and asked for time to present previous contributions. The team agreed to document these policies in the main contributions file.

### Borscht Serialization Format Proposal

David presented a proposal to adopt Borscht as a serialization format for FAB encoding, explaining that Borscht is a mature, well-documented format that is a perfect superset of FAB and can provide compatibility guarantees while accelerating the development process. He demonstrated that FAB is already a strict subset of Borscht, producing identical byte outputs for supported data types, and proposed that the improvement protocol should specify this Borscht subset implementation. David offered to provide a working implementation, Bosch schema, and test cases to help transition to this new format.

### FAB and Borscht Serialization Discussion

The team discussed serialization formats, focusing on field-aligned binary (FAB) and its relationship to Borscht. Kevin explained that while FAB is specified in the ledger and cannot be changed, they can specify the translation of compact data types into FAB. The group agreed that using an existing schema like Borscht would be beneficial, though there are some wrinkles around efficient in-circuit serialization of base types like SECP256K1 points. Andrzej and Jonathan confirmed that Borscht's structure was likely not coincidental, as earlier versions of Midnight Ledger had used Borscht as their internal serialization format.

### Borscht Compatibility Implementation Discussion

The team discussed implementing Borscht-compatible descriptions for exported structures, with David proposing a short-term commitment to using Borscht encoding rather than promising stability with specific curve types. Kevin agreed this approach was feasible and would write the COIP with this in mind, likely adding David as a co-author. The discussion concluded with Parisa noting an ongoing issue about the relationship between private estate and private events that needed further discussion with the appropriate stakeholders.

### Compact Language Implementation Discussion

The team discussed several key topics related to the compact language implementation and development. Kent and Jonathan highlighted the need to address private state and events, with Jonathan noting that the current private event description presents a research problem that will require defining specific use cases. The group debated Yurii's proposal to add a Rust compact runtime, with Kevin and Joseph expressing concerns about maintaining both TypeScript and Rust runtimes simultaneously. The team also discussed the upcoming transition to the new ZKIR repository and the need for a formal specification. Regarding serialization and deserialization formats, Kevin suggested creating a COIP to officially commit to the serialized format, which would be equivalent to Borscht. The conversation ended with a discussion about intermediate representation for downstream projects, with Kevin clarifying that while the team is interested in this approach, any representation should be considered an implementation detail rather than a stable external format.

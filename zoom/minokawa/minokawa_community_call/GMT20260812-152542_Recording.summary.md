### FAB Serialization Format Stability Discussion

The team discussed stabilizing the FAB (Field Aligned Binary) serialization format used for cross-chain transactions, particularly regarding its consistency with the persistent hash implementation. David raised concerns about potential security vulnerabilities if the format changes, noting that the current specification allows for instability on minor version increments. Kevin clarified that while persistent hash guarantees stability in terms of using SHA-256, it doesn't guarantee preservation of struct layouts between compact compiler versions. The discussion focused on establishing stability for off-chain serialization and deserialization processes, particularly for handling Ethereum return values that need to be deserialized in circuit after being serialized off-chain.

### Serialization and Maintainer Processes

The team discussed two main topics: serialization and deserialization functionality, and maintainer status processes. For serialization, Kevin and David agreed to specify the encoding for compact types and version the serialized format to handle future changes and maintain compatibility. Regarding maintainer status, Kevin proposed creating a documented process similar to LFDP projects to allow more contributors to gain maintainer rights, though Kent raised concerns about maintaining quality standards. The conversation ended with a brief mention of submitted COIPs, including log expression for structured event emission and explicit visibility modifiers.

### Language-Agnostic Contract Representation Discussion

The team discussed the need for a language-agnostic contract representation, with Kent and Kevin expressing that it's too early to standardize on anything. Kevin shared lessons learned from the Dart project and recommended allowing developers to use existing unstable versions like Elmo Disclose. Joseph suggested extending ZKIR as an alternative approach, but Kent argued that ZKIR is too low-level for arbitrary backends and that a higher-level intermediate language would be needed. The group agreed that while standardization is premature, someone could experiment with creating a new backend to help determine the optimal characteristics for such a representation.

### Rust Backend Development Proposal

The team discussed a proposal from an author regarding developing a Rust backend for compact contracts. Kevin suggested that the author could become a maintainer and contribute the backend as part of the Minokawa project rather than developing it unofficially. Parisa agreed to ask the author to watch the discussion and have a further conversation about their desired level of ownership and the format they want to use.

### Open Zeppelin Proposal Discussion

The team discussed a proposal from Open Zeppelin regarding export keywords in modules, with Kevin and Kent agreeing that the proposal misunderstands how modules work and should not be implemented. The group then addressed Rodrigo's request to extend the contract info JSON file to support multiple SDKs, with Kent suggesting a hook mechanism that would allow capturing the output of specific compiler passes without committing to versioning the intermediate language. The team agreed to explore options including compiler flags and binary serialization of IR forms, with Rodrigo tasked to propose specific implementation approaches that would work for long-term integration.

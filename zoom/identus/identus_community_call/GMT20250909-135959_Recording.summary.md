### Cardano VDR Specification Overview

Fábio presented a specification for VDR using Cardano as the source of tools, which is similar to the existing Deed Prism specification. He explained that the new specification creates a new type and model in Protobuf for storing data, allowing for immutable data modification through a chain of transactions on Cardano. Fábio emphasized that the specification adds a new key type for signing and includes rules for creating and updating operations, requiring a master key for self-signing and consistent validation. Yurii highlighted the importance of these constraints for maintaining consistent results and preventing orphan data.

### Event Notation and Validation System

Fábio explained the notation system for events, where events are referenced by position rather than name, and demonstrated how a chain of events is created with each new event referring to the previous one. He described the validation process where only the oldest valid chain on the blockchain is accepted, and explained that events must be signed with a VDR key and maintain a finite state that cannot be activated once deactivated. The discussion concluded with Fábio outlining the structure of event fields, noting that fields 1-49 are required for validation while fields 50-99 contain metadata that indexers don't need to care about.

### Event Validation and Data Extraction

Fábio explained the process of validating events and extracting data, which involves three main steps: grouping events by identity, building a valid chain of ordered events, and extracting data from the validated chain. He described the rules for validating events, including the need for specific fields to be present, signed with the VDR key, and owned by the correct key type. Roberto asked about the signing process, and Fábio clarified that the entire event structure, including metadata, is signed as a whole, not just the first event type.

### Cardano Blockchain for Data Versioning

Roberto and Fábio discussed the use of Cardano blockchain for data versioning and asset management. They explored how events on the blockchain can be used to track changes to a document or file, with each update creating a new event while maintaining the same reference. Yurii suggested specifying a special resource for this purpose, similar to revocation lists in SSI. Fábio explained the process of indexing events, validating data fields, and preserving compatibility with previous steps. They agreed that this approach could provide a single point of truth for data references while allowing for versioning and metadata tracking.

### Data Change Validation Process

Fábio explained the validation process for data changes, which can be handled on mobile systems or similar platforms. He described how the system currently supports two types of data changes: replacing bytes and updating strings, but these could be expanded to include more complex operations like patch-based updates or partial data modifications. Roberto clarified that while the system is designed to handle patch-like updates, there's nothing preventing users from replacing entire byte arrays in a single transaction if needed, which could be useful for optimizing transactions or handling large data transfers.

### Blockchain Data Reservation System Design

The team discussed the design of a system that allows users to reserve large numbers or add custom sections, using mechanisms like the indexer and validator. Jon raised a concern about the maximum size of data that can be transmitted in a smart contract transaction, emphasizing the resource constraints of the blockchain. Roberto clarified that the system would allow for flexible use of reserved positions, with the indexer validating specific entries while ignoring others. Fábio mentioned adding constraints for the indexer, such as the need for a settled time behind the blockchain and space limitations.

The team agreed that the basic implementation is in place, with some bugs to be fixed, and they will continue to brainstorm the best way to integrate this into the Identus platform in future discussions.

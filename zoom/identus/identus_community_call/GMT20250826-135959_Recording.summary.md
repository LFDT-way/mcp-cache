### Login Flow Implementation Options

The team discussed different implementation options for login flows, with Yurii suggesting multiple approaches including Didcom, DC extension, and custom solutions. Gonçalo expressed concerns about overcomplicating the implementation by using Didcom, advocating for simpler solutions like Tradecom or OIDC. The discussion focused on the balance between adding dependencies on the app side versus the server side, with Fabio explaining that the client only shows the QR code or deep link while the server handles the Didcom communication.

### Decentralized Authentication Protocol Discussion

Gonçalo and Fábio discussed a login flow using email authentication and decentralized identifiers (DIDs). Gonçalo proposed a direct peer-to-peer authentication method without a server, while Fábio emphasized the importance of understanding the underlying protocols and challenges. Yurii suggested extending the protocol with other DID.com protocols for authentication and authorization. The discussion highlighted the complexity of implementing DID.com libraries in SDKs and the need for further exploration of the proposed login flow.

### Didcom Library Key Management

Gonçalo and Fábio discussed the process of resolving deeds and handling private and public keys using the Didcom library. They clarified that the server does not need to store its own private keys but must be able to resolve the keys of user deeds and verify the validity of user agent replies. Fábio emphasized the need to create a challenge and define a protocol for communication between the server and the wallet, which Gonçalo suggested could be implemented using simple JSON.

### Authentication Protocol Design Discussion

The team discussed authentication protocols, with Gonçalo expressing concerns about adding complexity to Didcom and suggesting a more generic JSON-based approach that could be adapted for different protocols. Yurii proposed creating a document with diagrams to present to the community for review, while Fabio noted the need to address session logout functionality. The discussion concluded with Yurii emphasizing that authentication and authorization are typically sequential steps, though Gonçalo preferred to focus on authentication first without adding authorization complexity at this stage.

### Decentralized Authentication and Authorization Challenges

The group discussed the complexities of authentication and authorization in decentralized identity systems, particularly focusing on the role of deeds and controllers. Gonçalo and Fábio debated how to implement authentication with deeds while maintaining the principles of Self-Sovereign Identity (SSI), where individuals control their own credentials. Yurii explained how a mobile wallet deed could be used for authentication to create an account, but noted that additional flows and onboarding activities would be needed for specific actions and credentials. The discussion highlighted the challenges of replicating traditional email-based authorization in a decentralized identity system.

### Comparing Email and VC Logins

The team discussed the differences between logging in with email credentials versus logging in with VC (verifiable credentials). Gonçalo and Yuri debated the need for arguing access to resources like ChatGPT when using company-issued VCs, while Fabio explained that self-sovereign identities (SSI) decouple identity from permissions, unlike email-based systems. The discussion concluded with Gonçalo emphasizing the potential limitations of SSI for accessing private company servers, suggesting that "login with VC" offers more flexibility than traditional login methods.

### Authentication Protocols Evaluation Meeting

The team discussed different authentication protocols, focusing on the advantages and limitations of Didcom and VC. Gonçalo emphasized that while Didcom is not widely used, it can be adapted to various protocols, including VC. Yurii confirmed that VC login would include authorization, unlike other methods. The group agreed to further define the specific authentication process and consider feedback from the Didcom community before making a final decision.

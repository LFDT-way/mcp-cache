## Overview

<p>The team discussed the GitHub org splitting and security considerations, focusing on how to manage different types of projects within their organizational structure while maintaining appropriate security standards. They explored the possibility of creating separate organizations for core and ecosystem projects, with discussions around defining what constitutes a core component and establishing clear guidelines for project transitions between different organizational structures. The team also addressed practical considerations including licensing costs, repository management, and the need for clear policies and processes to support both core and ecosystem projects while encouraging community involvement.</p>

## Details

### Repository Security and Metrics Discussion

Jessica led a discussion about repository splitting, emphasizing the importance of security considerations. The team discussed how their current security tools are configured to be meticulous about what gets shared and included in licenses. Jessica raised questions about the implications of including non-core repositories in their security configuration and how this might affect their OpenSSF status. The group also touched on the challenges of consolidating metrics across different organizations for a single project, noting that Bitterjet may have a solution. Diane highlighted the core issue as whether to include non-core Hiero projects in the extended security provided for core projects.

### GitHub Security Organization Challenges

Nathan explained that GitHub's organizational structure lacks granularity for managing security requirements and permissions, making it challenging to apply different policies to subsets of repositories. He suggested creating separate organizations, such as an ecosystem or incubating org, to accommodate projects with varying security standards. Diane clarified that core Hiero projects would require extended security coverage, and Nathan confirmed that including non-core Hiero projects in the same organization would increase licensing costs due to per-developer charges.

### New Project Separation and Guidelines

The team discussed separating out a new project from the Hiero Ledger organization, with Diane noting that Fabric Labs provides a precedent for this approach. They agreed that the TSC would need to vote on the separation, and the naming convention for the new organization would be important, with "Dash Eco" being considered. Nathan and Jessica highlighted the need for clear security protocols and tech tag guidelines for both the core and ecosystem organizations, as well as a policy for what can be admitted into each. They also reviewed the current projects covered by the core organization, noting that Python SDK and some DID SDKs were community contributions.

### Python Package Security and Structure

The team discussed moving certain Python packages and repositories to different locations, with Diane emphasizing the importance of the Python SDK and digital identity components conforming to higher security standards. Jessica mentioned she would draft a document for the TSC regarding the proposed two-organization structure, which seemed to be gaining consensus despite Diane's initial objections. The group also discussed the need to establish guidelines or processes for projects in the ecosystem to work their way into the Hiero Ledger or remain in the ecosystem as long as they wish.

### Ecosystem Project Governance Structure

The team discussed the structure and governance of community projects within the ecosystem, focusing on the potential creation of a "labs" or "incubation" structure. Diane emphasized that the ecosystem is not temporary and projects should only be removed if they fail or lose traction, while Nathan suggested a pathway for projects to transition from the ecosystem to core if they meet certain criteria. The group agreed that defining what constitutes a "core" project is crucial, with Nathan highlighting the high bar for projects like SDKs due to their potential impact on ecosystem trust. Jessica raised concerns about how the naming and promotion of projects might affect perceptions of inclusivity and diversity within the ecosystem.

### Hiero Network Core Projects Discussion

The team discussed the definition of "core" projects for the Hiero network, with Diane and Joseph agreeing that core components should include consensus nodes and mirror nodes, while non-core items like SDKs should be separate. They explored the possibility of transferring projects hosted on the Hiero ledger to the Eco system, with Diane noting that only solo actions might need to move over. Nathan raised concerns about the cost of managing and maintaining new repositories, highlighting that current management by Roger and Andrew is not sustainable in the long term, and Jessica agreed to discuss with David about potential LF resource costs for administration.

### Core vs Ecosystem Projects Classification

The team discussed the definition and classification of core versus ecosystem projects, with Nathan and Diane agreeing that core components should include SDKs for consensus nodes, Python SDK, and Solo, while ecosystem components would include Solo Action and hashgraph online pieces. They decided to present different definitions of core to the TSC for policy clarification, with Diane suggesting they could stage options and ask for decisions on where specific projects should be housed. The discussion also touched on security requirements and budget constraints, with Nathan emphasizing the need to consider both security and financial aspects in their decisions.

### Sandbox Initiative for Community Projects

The team discussed the process of managing new projects and the potential creation of a sandbox for experimental projects that don't meet security standards. They agreed to frame the initiative as lowering the bar for entry to encourage community involvement rather than lowering standards. Jessica will draft a proposal for the tech team, aiming for submission by July 31st, with Diane planning to add input before the tech team's review. The group also discussed defining core components of the network and additional security tools, with Nana suggesting a clear distinction between these groups and other projects.

### Repository Migration and Cost Planning

The team discussed moving repositories between core and ecosystem projects, with Diane emphasizing the need for diplomatic communication due to existing infrastructure dependencies. Jessica mentioned having two proposal documents to share with the team, and Nathan agreed to investigate licensing costs for adding new projects, including both security features and hardware costs. Nathan will work with Chad to compile detailed cost data over the next week, which will be needed for budgeting and future TSC discussions, particularly regarding Hedera Foundation funding.

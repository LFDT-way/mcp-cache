## Overview

The team discussed the proposed splitting of Hiero core and ecosystem projects into separate organizations, with concerns raised about security configurations, resource management, and different standards for core versus ecosystem projects. Various models for managing core and non-core code were examined, including Fabric's approach with separate labs and Bayzoo's single-repository differentiation, leading to discussions about security requirements and governance needs. The group agreed to develop a formal proposal for the TSC, with plans to include Richard in future working group discussions to align on technical details before presenting the final proposal.

## Details

### Repository Split Rationale Discussion

Jessica discussed the need for better clarity on the main purpose of splitting repositories into two organizations, citing concerns about security configurations and resource management for community projects. She mentioned that Hendrik, who was unavailable, had raised this point and had a conversation with Richard about the proposed split, though the details of that conversation were unknown. Jessica expressed her intention to align everyone on the reasons for the split and to determine whether it was driven by security concerns or the goal of boosting collaboration through an incubation model.

### Hiero Core and Ecosystem Separation

The team discussed the need to separate Hiero core and ecosystem projects into different organizations due to security and financial considerations. Nathan explained that while both core and ecosystem projects would be held to different security standards, core projects would be subject to more stringent Hiero standards, while ecosystem projects would meet Linux Foundation minimum standards. He emphasized that the separation would allow for easier onboarding of ecosystem projects without requiring them to meet the higher financial and security requirements of core projects.

### Organizational Split Proposal Discussion

The team discussed concerns about an organizational split, with Jessica noting that Richard and Hendrik had strong opposition to it. Nathan explained he had been too busy with a new critical path project to discuss the matter with Richard. The group agreed that as a working group, they should prepare an actual proposal for the TSC rather than having individual conversations with TSC members. David, who was new to the discussion, clarified that the goal was to identify code with different requirements and rigor, and suggested using the term "core" rather than "community-driven" to describe the projects in question.

### Core vs. Non-Core Code Management Approaches

David shared examples from the Fabric and Bayzoo projects to illustrate different approaches to managing core and non-core code. He explained that Fabric uses a model with a core repository and separate "labs" for experimental code, while Bayzoo differentiates code within a single repository. Jessica emphasized the benefits of using established models to meet technical expectations and align with the project's path. Hendrik and Nathan discussed concerns about using two separate organizations, with Hendrik noting that Richard shared similar views. Nathan highlighted that Bayzoo still applies the same security controls across all code, suggesting that they might need to adopt a model more like Fabric's in the future.

### Project Security Tier Requirements Discussion

The team discussed the need for different security and governance requirements for projects in the core versus the ecosystem. They clarified that this is not about creating an incubator, but rather about having different levels of requirements based on the type of project and its needs. The group agreed that the next step is to define what these different requirements should be and why they make sense, rather than just splitting projects based on security alone.

### Core Onboarding Challenges and Funding Solutions

The group discussed the challenges of onboarding projects into the core, particularly regarding security standards and funding requirements. Hendrik expressed concern about excluding projects based on financial ability, while Nathan explained that higher security and governance standards inherently carry costs. The discussion concluded with a proposal for the Hedera Foundation to provide a dedicated funding pool for community projects that meet core requirements but lack funding, rather than requiring individual project funding.

### Fabric Model Challenges and Solutions

The team discussed challenges with using fabric as a model and considered reaching out to fabric maintainers for insights. David suggested speaking to specific maintainers like Marcus or Dave for their perspectives, while Hendrik questioned whether this should be raised in a tech meeting. They also explored how other projects like Kaleido handle similar issues, with David mentioning Kaleido's recent Firefly release and Cardano connector feature. The group agreed that raising these questions on the tech channel could provide valuable input from a wider range of contributors.

### GitHub Organization Security Structure Evaluation

The team discussed the security implications of organizing projects within a single GitHub organization versus splitting them into multiple organizations. Nathan explained that while splitting projects could improve security by creating organizational boundaries, it would also increase management overhead. He cited examples like PyTorch's recent decision to split its projects into multiple organizations due to security concerns. David noted that Hyperledger was originally set up with a single organization structure, but has since started spinning off projects into separate organizations. The team also discussed the potential impact of security audits on the entire organization, with Nathan explaining that auditors would examine all projects and third-party dependencies.

### Security Audit and Repository Split Planning

The team discussed the need for a common understanding of the security audit requirements and repository split proposal. Hendrik, Nathan, and Joseph agreed to invite Richard to join their working group call to align on the technical details before presenting a draft proposal to the TSC. They decided against including the TSC in the current discussion to avoid complications, with Nathan noting that any proposal would likely take a few weeks to develop. Jessica agreed to hold off on reviewing the proposal until after the working group meeting with Richard.

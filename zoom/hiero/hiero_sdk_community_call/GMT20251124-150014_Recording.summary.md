### SDK Key Encoding Standards Review

Robert presented a review of key encoding standards across SDKs, focusing on ED25519 and ECDSA formats. He conducted an audit to compare how different SDKs generate and encode keys, particularly examining DER encoding and ASN1 structures. Robert explained the basics of ASN1 and DER encoding, including their roles in defining and encoding key structures, and shared examples of current key container standards like PKCS8, X509, and SEC1.

### SDK Key Encoding Structure Variations

Robert discussed the differences in key encoding structures between various SDKs, focusing on ED25519 and ECDSA. He explained that while most SDKs (C++, Swift, JS, and Rust) use the same standardized structure for ED25519 keys, Java and Go use a different legacy structure for ECDSA keys. The discussion highlighted how even though the data being stored is the same, the different encoding methods result in different byte sequences when DER encoded.

### SDK Key Packaging Compatibility Issues

Rob presented findings on key formats across different SDKs, noting that while all implementations are standards-compliant, differences in key packaging, particularly for ECDSA, can cause compatibility issues. He demonstrated that while most SDKs can import and use keys from other languages, some pairs, such as Java and C++, cannot successfully import each other's ECDSA private keys. The team agreed that finding a consistent way to package keys would help alleviate confusion and improve compatibility.

### PKCS8 Format for Private Keys

Robert and Hendrik discussed the possibility of using PKCS8 format for all private keys to ensure cross-compatibility, eliminating the need for different formats like X509SPKI. Robert mentioned that modern crypto libraries should support various formats, but he hasn't tested this himself. Keith raised concerns about distinguishing between ECDSA and other key types, questioning if this issue is a significant problem for developers. He suggested focusing on more pressing issues, as many platforms already use open create for ECDSA keys.

### SDK Key Format Standardization Discussion

The team discussed the need for a unified definition across all SDKs for key formats and encodings, emphasizing consistency in how keys are imported and exported. Hendrik proposed focusing on establishing a common baseline for version 3 SDKs, while Keith raised concerns about the compatibility of third-party libraries and the complexity of generating keys that the SDKs can handle. The discussion highlighted the challenge of balancing standardization with flexibility, with Keith skeptical about the feasibility of supporting a wide variety of key formats.

### SDK Key Format Compatibility Investigation

The team discussed issues with key formats and compatibility between different SDKs. Keith suggested testing third-party libraries to verify if the SDK can accept generated keys. Hendrik and Robert explored the possibility that the problem might lie in the crypto libraries used by each SDK. They agreed that further investigation into the crypto libraries at the SDK level is needed to identify and resolve the issues.

### SDK Key Import Functionality Review

The team discussed potential issues with their SDKs and libraries, focusing on import and export functionality for keys. Hendrik suggested creating small examples for each library to test import and export capabilities, aiming to prove that any problems lie within the SDKs rather than the crypto libraries. Keith raised questions about the use cases for importing keys from third-party libraries, suggesting that users with deep knowledge of the libraries could specify key types and formats more precisely. The team agreed on the importance of consistency across SDKs and considered enhancing support for importing different types of keys, though Keith expressed preference for the current simplicity of the SDK's key import functionality.

### SDK Key Format Standardization Discussion

The team discussed key format standardization across their SDKs, with Robert presenting research on different key container formats like PKCS8 and X509SPKI. Keith expressed concerns about using DER encoding for ECDSA keys, noting it makes their keys incompatible with other EVM wallets, and suggested moving away from DER encoding in favor of the standard 0x-prefixed key format used by most Web3 wallets. The team agreed to continue research into crypto library capabilities and explore a path forward for standardizing key formats, with Robert planning to present more details in the next meeting.

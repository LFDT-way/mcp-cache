## Overview

The meeting focused on SDK community updates and the TCK GitHub Actions proposal. Keith and Hendrik confirmed that a vote for a new junior committer in the JavaScript repo was nearly complete and would likely pass. The group discussed the use of separate Discord channels for each SDK, with Hendrik arguing that maintaining them was manageable and useful for active communities like Python. Keith shared that usage metrics for C++, Swift, and Rust SDKs showed very little activity on the Hedera network, leading to a discussion about whether to archive those repos or find new maintainers. Daniel argued for keeping Swift due to its potential in wallet development, while Hendrik favored keeping Rust because of its growing popularity. Ivaylo suggested creating MCP servers for SDKs, and Hendrik noted that a Hiero-specific MCP repository already existed. The main technical discussion centered on two different GitHub Actions implementations for TCK backward compatibility: one from the Hiero Hackers team and a lighter version from Ivaylo. Keith and Hendrik raised concerns about maintenance, where the code should live, and the complexity of the current TCK implementation. The group agreed that a formal design proposal was needed to resolve the differences between the two approaches.

## Details

### JavaScript Junior Committer Nomination Discussion

The SDK community call discussed a nomination for junior committer in the JavaScript repository. Hendrik clarified that the voting process requires a two-week waiting period after which GitVote will automatically create a result. The group confirmed that majority voting is required, with no specific minimum threshold mentioned.

### Committer and Maintainer Nomination Process

Keith and Hendrik discussed the process for nominating new committers and maintainers, clarifying that anyone can initiate a nomination and vote, not just existing committers or maintainers. They noted that while anyone can create a nomination issue, it's ideal for nominees to present themselves in the community call to provide context for voters. The conversation also touched on challenges with monitoring multiple Discord channels for different SDK repositories, with Keith suggesting that a single consolidated Discord channel might be more manageable.

### SDK Channel Maintenance Discussion

Hendrik discussed the maintenance of multiple SDK channels, expressing concerns about merging them into fewer channels due to the complexity it would introduce. Keith clarified that separate Discord channels already exist for each SDK and proposed that repository maintainers should manage their own channels. Keith also noted that the C++, Swift, and Rust SDKs have low usage on the Hedera network and suggested finding additional resources to maintain these less active repositories. Hendrik requested that usage percentage data be made public to help address questions about SDK activity.

### SDK Maintenance and Metrics Planning

Keith announced plans to present SDK metrics at the next meeting, noting that only about 20% of transaction reports come from updated SDKs due to most users still using older versions. The team discussed the future maintenance of C++, Swift, and Rust SDKs, with Keith proposing to update READMEs to indicate lack of active maintenance and potentially archive or find new maintainers for these repositories. Hendrik expressed interest in continuing Rust SDK maintenance due to its growing popularity, while noting that the current team would need to improve their Rust knowledge to effectively maintain it.

### Swift SDK Archiving Discussion

The team discussed archiving the Swift SDK due to its limited current usage despite its potential future value as Web3 adoption grows. Keith clarified that archiving would not make the SDK inaccessible but would prevent adding new features, while maintaining existing functionality. Hendrik emphasized that archived SDKs could be unarchived if needed and could help streamline development focus on more actively used languages.

### GitHub Actions for TCK Implementation

The team discussed implementing GitHub Actions for the Technology Compatibility Kit (TCK) to ensure SDK compatibility. Two approaches were proposed: one involving a server component and another using a lightweight GitHub Action without Docker. The group agreed that the current implementation in the TCK root directory should be moved to a separate repository or subdirectory for better organization. It was decided to create a design proposal as an issue in the TCK repository to facilitate further discussion and agreement on the design before implementation. The team also briefly touched on the Python SDK TCK integration, which needs follow-up from the Python team.

Robert has been working on the C++ SDK, developing automation bots to auto-assign contributors to issues and track issue difficulty levels for new contributors. He has also implemented a bot to check DCO and GPG signatures on every commit, aiming to make the process more transparent for new contributors. Robert plans to refine the workflows and labels to further reduce maintainer workload.

### SDK Release and Testing Updates

The team discussed updates on RC tags, testing, and SDK releases. Ivan explained that a new beta version of the Java SDK was released, but releases for other SDKs were postponed due to potential API changes. Angelina reported ongoing issues with the Windows setup for the JavaScript SDK and is now trying to resolve it using Ubuntu. A meeting was scheduled for Wednesday at 10 am EST to address build issues across different systems, and Angelina invited team members to join. ### SDK Beta Release Management Discussion

The team discussed beta releases for SDK features, with Robert raising concerns about managing multiple beta releases for different features like Hooks and 1313. Ivan explained that beta releases are sometimes necessary to break dependency loops with other projects like the consensus node, while Georgi emphasized that beta releases should only be used when specifically requested by clients. The team considered two potential solutions: changing the consensus node's release process or implementing release branches, though the latter approach might conflict with Nathan's previous statements about avoiding such patterns.

### SDK Release Branch Strategy Discussion

The team discussed the release pattern for SDKs, with Ivan and Georgi explaining that previously, releases were done from a main branch, but this changed to using release branches. Robert noted that the current development process has become more complex, with alpha and RC builds being tested, which presents challenges for the SDK team. The group agreed that beta releases are acceptable as long as they are clearly marked as subject to change in the release notes, or features can be placed on a separate branch until completion.

### Beta Release Security and Management

The team discussed the challenges and risks associated with beta releases, particularly for SDKs. Georgi raised concerns about potential security risks if a beta release contains broken features, which could be exploited by malicious users. Robert suggested coordinating with Keith to better manage these releases and emphasized that the decision to do a beta release should ultimately be up to the maintainers of the respective repositories. Sophie shared their experience with the Python SDK, highlighting the difficulty of managing large releases and the lack of a retroactive release option on GitHub. The team explored the possibility of using pre-releases and AI tools to help review and test new releases more effectively, while also discussing the potential need to improve their release management practices to avoid future issues.

### Pre-Releases for SDK Development

The team discussed pre-releases and their potential use for SDK development. Robert suggested that pre-releases could be a good way to signal to users that a release is still subject to change, but emphasized that it should ultimately be decided by the maintainers. Ivan shared a specific use case where a pre-release could be beneficial for testing a configuration change. Sophie expressed uncertainty about whether the next release should be 0.11 or 0.12, noting that it would be a major release bump due to significant changes. The team agreed that pre-releases might be useful in rare cases, but they haven't identified a strong use case for them yet. Robert mentioned that Angie is working on tracking HIP progress for each SDK.

### HIP Implementation Tracking Tool

Angelina presented a tool tracking HIP (Hypersignature Protocol) implementations across SDKs, focusing initially on Python. She explained that while Java has made good progress with HIP implementations, other SDKs like Python and JavaScript are lagging. Angelina is working with Robert to expand the tracking to include additional SDKs and historical HIPs, and she invited others to contribute information about implemented HIPs. The tool includes a field to specify which HIP each issue implements and shows whether issues are in progress or completed. Angelina plans to create a HIP implementation template across SDKs that would guide users through the process and connect them with resources for help.

### HIP Progress Tracking and Training

The team discussed tracking HIP (Hyper-Island Project) progress and agreed to create an epic in the SDK hub to link to GitHub issues for each SDK. Angelina plans to develop a comprehensive training guide and knowledge base for HIP implementation, aiming to increase community engagement and participation. Sophie expressed interest in using the new tools to better understand and implement HIPs, particularly for the Python SDK. The team also discussed potentially developing HIP teams for each SDK to manage implementation and tracking.

### Enhancing HIP Contributor Accessibility

The team discussed making HIP (Highly Important Proposal) implementations more accessible to different contributor levels. Robert emphasized that full HIP implementations should include comprehensive testing and examples, while Angelina proposed creating simpler issues for beginners by focusing on testing tasks after the main implementation is complete. They agreed to continue the discussion at the next meeting, with Robert adding that HIP-related topics would be included on the agenda for the following week.

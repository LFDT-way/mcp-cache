### SDK Updates and Developer Initiatives

The SDK community call focused on updates for the Swift and C++ SDKs. Robert announced that Swift 6 support would be added in two weeks, with the official release scheduled for February 2nd. For the C++ SDK, Robert highlighted the success of the good first issues initiative, which has attracted new developers and contributed to the closure of several issues. The team is now working on maintaining a steady flow of beginner-level issues to encourage continued contributions from new contributors.

### HIP 1261 and Pectra Design Updates

The team discussed the status of HIP 1261, which is in PR state with passing CI but cannot be merged due to dummy endpoint data. Ivaylo presented a design proposal for Pectra, which includes a new Type 4 transaction with authorization list and updated APIs for account creation and update, though the PR cannot pass CI due to missing tag. Robert inquired about Rust progress, which Ivaylo will follow up on with Georgie. The team also noted that Ethereum Type 4 transaction support is planned for consensus node version 0.72.

### Version 73 Release Planning

The team discussed the release timeline for version 72, noting that a more reasonable version would be 73 in March or April. They reviewed progress on Java and Go implementations of new transaction types, with both languages successfully executing the new transactions but still pending the addition of new properties in account creation and updates. Robert proposed standardizing issue labels across SDKs to create a consistent contributor experience, suggesting a base set of labels like "good first issue," "beginner," "intermediate," "advanced," "new feature," and "documentation" that could be expanded by individual repos.

### Standardizing Good First Issues

Keith and Robert discussed the need for consistency in good first issues across all Hiero repositories, with SDKs serving as an initial playground for establishing these workflows. Robert plans to create a template or guidelines document in the SDK Hub, outlining standardized labels with descriptions and color hex codes, which will be open for review and adoption by SDKs.

### SDK Repositories Transition to Solo

The team discussed transitioning SDK repositories to reference Solo instead of local node in READMEs and documentation. Keith will open issues in relevant repos to update references, while Venilin reported that the JavaScript SDK now uses Solo for local development with deterministic test results. Angelina provided an update on the Python SDK, noting its growth through the GFI initiative with multiple contributors and recently closed beginner and intermediate issues.

### Python SDK Development Updates

Robert discussed his plan to contribute to the Python SDK by addressing good first issues, aiming to alleviate workload. Hendrik inquired about transitioning from local node to Solo as a development dependency, noting Solo's improved usability and the creation of two special commands for testing. He suggested integrating these commands into SDK documentation for easier local testing. Keith expressed concerns about Solo's quick start process, suggesting users should read prerequisites and noting compatibility issues, particularly on Windows, before attempting the quick start.

### Improving Solo Testing Tool Experience

The team discussed challenges with Solo, a testing tool for SDKs, particularly around its installation and setup process. Keith expressed concerns about the current state of Solo's documentation and user experience, suggesting that SDKs should simply link to Solo's getting started page rather than attempting to provide their own quick start guides. The team explored potential improvements to Solo's functionality, including the ability to create additional accounts with large balances for testing purposes. Robert and others shared their experiences with using Solo in CI pipelines and development workflows. The conversation ended with a brief discussion about issue labeling conventions, where Angelina and Robert agreed that issues requiring Solo or TCK testing should be labeled as intermediate or above, while unit testing could remain at the beginner level.

## Overview

The SDK Hyro community call focused on discussing a new GitHub Action proposal for TCK testing presented by Daniel and Manish. The proposal aims to automate TCK testing in CI pipelines to simplify the review process for SDK developers, particularly helping maintainers who may not have the hardware resources to run local tests with Solo nodes. Key concerns raised included the potential for a single external repository to become a bottleneck, the need to integrate with existing CI workflows, and ensuring the solution can handle new features that need to be added to both SDKs and TCK. The team agreed to add a motivation section to the proposal and continue discussions about implementation approach. Keith also announced updates on the HTTP transport layer design for MirrorNode account balance queries and introduced HIP 1535, a new protocol called Clipper that will require significant SDK support for channel creation, endpoint management, and message submission, with an initial release planned for December. Finally, Keith addressed Jessy's request to become a junior committer for the JavaScript SDK and committed to initiating the necessary voting process.

## Details

### SDK Landscape and Initiatives Discussion

Keith welcomed attendees to the SDK Hyro community call and introduced himself as a product manager at Hashgraph who oversees SDK product direction. The meeting focused on discussing the SDK landscape across all supported SDKs, including new initiatives and projects. A key topic on the agenda was a new GitHub Action Proposal for the TCK that was presented in the previous week's TSC, with Danielle expected to discuss it further.

### TCK Automation Proposal Presentation

Manish presented a TCK proposal that aims to automate CI testing against the SDK's TCK implementation and Hiero SDK implementation. He explained that the current TCK testing process relies on unit testing and is difficult to review when new methods are implemented or logic is refactored. The proposed solution uses a mirror action to set up a solo network with a mirror node enabled and runs TCK tests against the implementation in CI.

### CI System for Code Reviews

The team discussed the purpose of a new CI system designed to assist reviewers in the code review process. Manish explained that the system would automate running the full test suite against PR implementations, eliminating the need for reviewers to clone branches and run tests locally, which would help maintainers who might not have the necessary capabilities on their machines. The system aims to simplify the review process by providing visibility into test case passing status directly in the CI environment.

### SDK Feature Implementation Discussion

The team discussed whether to implement a new feature in a separate repository or within the SDK repositories. Ivaylo advocated for implementing it in each SDK repository to ensure consistency across different versions and use cases, while Daniel suggested using an imported action to streamline implementation across repositories. Ivaylo expressed concerns about potential issues with shared CI implementation in a separate repository affecting all SDKs, though the discussion ended abruptly before reaching a conclusion.

### Feature Implementation and Testing Concerns

Mustafa expressed support for the proposed idea but raised concerns about implementation, suggesting the logic should check for changes in the cheesecake and recommending against creating additional repositories to avoid errors. Keith questioned how the proposed feature would handle testing new features that haven't been added to the TCK yet, to which Mustafa explained the current multi-step process involving adding test scenarios in the TCK repo and implementing new endpoints in SDKs. Daniel agreed with Mustafa's points about the need to add new functionality to both the SDK and TCK repositories for proper testing.

### JSON RPC TCK Implementation Discussion

The team discussed implementing a JSON RPC solution for TCK testing, with Mustafa suggesting it should be integrated into existing repositories rather than creating a new one. They explored options including adding a new folder to existing repos or implementing it as a new action in the SDK repo itself, with Mustafa advocating for the latter approach as cleaner and faster. Keith summarized the proposed workflow where developers would run TCK tests through a GitHub action before merging PRs, aiming to reduce TCK failures after PR approval.

### GitHub Action SDK Testing Proposal

The team discussed a GitHub Action proposal for SDK testing, where Mustafa explained that the current process requires manual local testing and verification before creating PRs, which could be automated through this proposal. Keith suggested adding a motivation section to the proposal to clarify benefits and use cases, which Daniel agreed to include. The team decided to continue discussions on the hashgraph line SDK team about potential integration and will take time to review the proposal further.

### SDK Development and Protocol Updates

The team discussed technical requirements for SDK development, particularly focusing on computer specifications needed for review processes and the implementation of MirrorNode account balance queries using a new HTTP transport layer architecture. Keith announced that three SDKs have implemented the MirrorNode account balance query based on this new architecture, though existing MirrorNode queries like gas pricing will not be retroactively updated. The team also reviewed a new protocol called Clipper (HIP 1535) being developed by the Hashgraph team, which will require significant SDK support including channel and endpoint management features, with an initial release planned for December and a corresponding design proposal expected this week.

### JavaScript SDK Committee Updates

Keith agreed to initiate a vote to make Jessy a junior committer to the JavaScript SDK and will discuss this with Hendrick. The team decided to continue following up on the GitHub Actions proposal for the TCK and will review the Clipper SDK proposal in next week's meeting. Keith advised against working on HIP 1195, suggesting instead to focus on new Clipper work and implementing MirNode account balance query support across the SDKs.

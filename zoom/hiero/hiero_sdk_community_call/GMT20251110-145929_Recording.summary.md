## Overview

The team discussed changes to meeting structures and publishing workflows for SDKs, including a new pull request for project meetings and a planned transition in publishing order for Rust and JavaScript SDKs. They explored challenges around key algorithms and encodings in SDKs, discussing potential solutions for handling different key types and encoding formats while considering future flexibility. The team agreed to define supported encoding types and create a reference guide for consistent key handling across SDKs, with plans to invite additional team members for further input on key structures and implementation details.

## Details

### Project Meetings Location Change

The team discussed moving the location of meeting agendas, with Hendrik confirming they were moved to the TSC and that Jessica had opened a pull request to create a structured project meetings system in the governance repo. The discussion focused on reviewing Jessica's pull request which included setting up project meetings for marketing and community engagement, with Hendrik approving the structure she proposed.

### SDK Publishing Workflow Transition

The team discussed changes to the publishing workflow for Rust and JavaScript SDKs, with Roger explaining that the order of publishing would be reversed to first publish to Hiero Ledger and then to Hashgraph, as part of a transition planned for January. Robert confirmed this would not be a breaking change but would require coordination between the JavaScript and Rust teams to handle potential merge conflicts. Roger clarified that while the functionality would remain unchanged, the change would affect all source code files that currently import from Hashgraph. The team also briefly discussed an upcoming event scheduled for the 12th and 13th, with Roger considering whether to move it to the 13th and 14th to avoid conflicts with the publishing updates.

### SDK Key Encoding Standards Discussion

Hendrik and Robert discussed the importance of specifying algorithms and encodings for keys in SDKs, as automatic detection may not be feasible for future algorithms. Hendrik shared a pull request that defines key algorithms and encodings, but questions remain about whether encoding specifications are necessary and whether the SDK should enforce strict input requirements. Robert noted that current SDKs can determine some algorithms based on encoding, but future key types may present challenges. The team agreed to further define input specifications and consider creating version 3 of the prototype specification to address these issues.

### Streamlining Developer Crypto Expertise

Keith and Hendrik discussed the challenges of making developers crypto experts and the need to simplify the process. They agreed that the current SDK works well with different key types but may need changes in the future to accommodate new algorithms like quantum-safe keys. Keith suggested making ECDSA the default and documenting how to use ED25519 keys. They also discussed the pros and cons of using DER encoding, with Keith advocating for its removal to simplify the process. Robert mentioned past issues with different SDKs using different DER encodings, which caused confusion.

### Algorithm Determination in String Methods

The team discussed challenges with determining key algorithms and encodings from string methods, particularly regarding the balance between simplicity and future flexibility. Hendrik proposed using enums for algorithms and encodings in GIN1, while acknowledging the complexity this could introduce. Robert suggested implementing a basic from-string method that uses DER encoding to determine the algorithm, which could simplify the user experience for common cases. The team agreed that this approach would allow users to input random key strings and have the method automatically handle the determination and processing.

### SDK Encoding Formats Alignment Discussion

The team discussed key encoding formats in their SDKs, with Keith expressing concerns about deer encoding causing user confusion due to its limited use in the Web3 ecosystem. They agreed to define supported encoding types, with Keith confirming that for ECDSA keys, both hex-encoded and deer-encoded formats should work as long as the correct prefix is used. Hendrik raised an issue about key input not working in the Java SDK, which Keith attributed to potential SDK-specific limitations, suggesting they should investigate and align the behavior across different SDKs.

### Hex vs DER Key Encoding Discussion

The team discussed the differences between hex-encoded keys with and without the 0x prefix, as well as DER-encoded keys. They noted that the starting characters (302 for DER, SWIO2 for hex without 0x) could help distinguish between formats, but agreed that a clear definition was needed. Ivan suggested consulting developers and community members to establish a clear goal for the changes, as the current objectives were unclear.

### Challenges in Defining Key Encodings

Hendrik and Keith discussed the challenges of defining key encodings and algorithms, noting that even experienced cryptographers struggle to consistently define them. Hendrik emphasized the need for a method that handles edge cases correctly, suggesting that specifying defaults or requiring explicit input might be necessary. Robert expressed uncertainty about contributing ideas without knowing future key types and suggested inviting Rohit for input. The discussion focused on internal methods and the potential for ECDSA keys as a default, with Hendrik mentioning a tax-encoded private key as a common starting point.

### ECDSA Encoding Methods Decision

The team discussed key encoding methods and agreed to expose two create methods: one for easy-to-use ECDSA with hex encoding, and another more flexible method that can handle different encodings. They decided to make the ECDSA method the default, while keeping the flexible method available for specific use cases. Robert noted that this approach would handle potential future key formats, though they agreed it was unlikely they would need to update the SDK within the next two years. The team also acknowledged current inconsistencies in key handling across their SDKs, which V3 would address.

### SDK Key Structure Standardization

The team discussed key structures and consistency across SDKs, with Sophie and Hendrik noting their limited expertise but agreeing that defaulting to ECDSA makes sense. They decided to invite Morit to the next meeting for further input on key structures. Keith presented a reference code sample guide to address inconsistencies in code samples across different platforms, proposing best practices such as using ECDSA keys with EVM addresses and consistent environment variable names. The team agreed to provide feedback on the guide, with Robert planning to share it in the SDK hub for public access.

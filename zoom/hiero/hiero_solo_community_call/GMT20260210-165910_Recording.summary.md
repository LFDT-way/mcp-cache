## Details

### Solo Benchmarking Suite Presentation

Keith presented a benchmarking suite for Solo that measures performance against local node and monitors key metrics. He shared two tests: a happy test and an EVM test, both involving account creation, smart contract deployment, token minting, and transfer. Keith sought feedback on his methodology and mentioned challenges with port errors on his Windows computer. The team discussed the potential need to take some discussions offline due to public recording and publishing.

### Solo Performance Test Design Discussion

Keith and Jeromy discussed the need for a synthetic test to analyze the run performance of Solo, focusing on transaction propagation times between consensus and mirror nodes. Keith explained that while local node uses record streams for a 500-millisecond round trip, Solo with block streams aims to achieve a similar speed, requiring configuration adjustments and testing tools. Jeromy suggested prioritizing this issue through the A5 program, acknowledging its importance while noting other pressing concerns. The conversation concluded with Keith seeking guidance on designing a suitable synthetic test for Solo's performance measurement.

### Write vs Read Transaction Pathways

Jeromy and Keith discussed the differences between write and read transactions in their system. They explained that write transactions go through the consensus node, while read transactions go through the mirror node. Keith noted that customer tests typically involve writing a transaction and waiting for it to appear in the mirror node. Jeromy suggested that bypassing the mirror node for certain read transactions could potentially speed up the process. They also discussed the role of the relay in bridging transactions and its impact on transaction responses.

### Solo Performance Testing Discussion

The team discussed performance testing for Solo, with Alex clarifying that Solo does not make transactions faster but enables previously impossible operations. Jeromy and Keith explored using the NLG network load generator plugin for Solo, which can simulate various transactions like EVM, NFT transfers, and smart contract operations. Keith expressed interest in learning more about the load generator and agreed to follow up with Alex and Jeromy for further information.

### Solo Node Upgrade Planning

The team discussed the upcoming changes to Solo and the need to upgrade it to support future versions of Consensus Node. They explored ways to improve Solo's performance, including a new feature called "ledger reset" that will allow for quicker network resets, and the implementation of caching for container images and helm charts to speed up installation times. The team also addressed issues with the messaging system in Mirror Node, particularly when using block mode, and discussed the challenges of transitioning from local node to testnet environments.

### Solo Memory Usage Investigation

The team discussed Solo's memory usage behavior, with Keith reporting that Solo increased from 8.5GB to 9.3GB over 6-8 hours during a one-shot deployment without any transactions being submitted. Jeromy explained that this could be due to gossiping between nodes and suggested comparing memory usage with older versions of the consensus node to ensure consistency in testing. The team agreed to investigate this memory usage issue further, particularly since it differs from Local Node's behavior. They also discussed the need to better document application ENV settings and the potential for Solo to be used as a production environment, which is different from Local Node's intended use.

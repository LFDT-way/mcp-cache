### Internal Meeting Advertising and SDK Issue

### EKS PVC Support Challenges

Nathan discusses the challenges with PVC support in Amazon EKS for multi-availability zone clusters. He suggests that Solo.io will need to provide the ability to specify taints, tolerations, and node selectors on a per-consensus node basis. Jeromy and Nathan debate whether this functionality has already been coded or is still in the pipeline. They conclude that helm chart changes will be necessary to make the definitions more granular, allowing for per-node and per-zone configurations. Nathan also mentions the potential need for custom storage classes per zone and per consensus node to work around the Amazon AZ issues.

### Solo Penetration Test Scope Clarification

Deepak discussed setting up an internal penetration test for Solo using Digital Ocean, but Jeromy and Nathan clarified that while Solo can run on various Kubernetes clusters including Digital Ocean, the scope of the penetration test should focus specifically on Solo's components rather than the underlying Kubernetes infrastructure. They explained that Solo's deployment is complex and testing should concentrate on aspects like ingresses, consensus nodes, and network exposure, while avoiding general Kubernetes security concerns.

### Blockchain Penetration Testing Scope

The team discussed the scope and approach for penetration testing, focusing on blockchain software components while avoiding unnecessary testing of Kubernetes ingress controllers and external infrastructure. They clarified the process for updating blockchain nodes, with Nathan explaining that consensus nodes can use a one-shot upgrade command, while mirror nodes and explorers can be redeployed statelessly. The discussion also covered the challenges with Block Node upgrades, noting that it remains experimental and requires alignment with consensus nodes, though a PR exists for the upgrade command.

### Solo Support and CLI Restructuring

The team discussed ongoing challenges with solo's support for different node versions, particularly regarding versions 63-65 which may have regressions. Nathan explained that while solo can run with any published version, only version 61.4 is fully tested and supported, and any issues with newer versions should be filed in the solo repo. The team also touched on the need to restructure CLI commands for quality of life improvements this quarter, which will include some breaking changes. Deepak mentioned his team's plan to shift testing from local nodes to solo, and Nathan confirmed that while solo can use any public version, they will triage any issues found in newer versions as they arise.

### Deterministic Images Implementation Strategy

Nathan and Deepak discussed the implementation of deterministic images for the Solo project, focusing on validation and security measures. They agreed that while current builds are self-validated, having multiple teams build and verify the images on different CI platforms would provide greater assurance. Nathan suggested starting with the SRE team building the deterministic image on Amazon and GCP CI systems, before expanding to council members. They also discussed the need to support other teams in building deterministic images for components like the mirror node.

### Deterministic Builds and Supply Chain Security

Nathan explained the concept of deterministic builds, highlighting that while they ensure reproducibility and integrity of build processes by preventing code injection during compilation, they do not address supply chain vulnerabilities tied to specified dependencies in the build manifest. He emphasized that deterministic builds are crucial for certifying that multiple builds across different hardware and environments produce the same output, ensuring the authenticity of container images post-build. Nathan also noted that deeper supply chain issues, such as compromised dependencies like Log4j, remain unresolved by deterministic builds alone and require additional measures like strict admission controls and dependency management.

### Open Source Change Control Challenges

Nathan and Deepak discussed the challenges of implementing strict change control processes for open source projects hosted on Hiero, particularly regarding dependency management and the use of Jfrog. Nathan explained that while such processes are viable, they would require either Hashgraph or Hedera to fund the Jfrog instance, as LF does not provide financial support for infrastructure services. He noted that projects like PyTorch have successfully implemented similar approval processes for dependencies, but only with the support of well-funded organizations and LF's assistance.

### Supply Chain Security Discussion

Nathan and Deepak discussed supply chain security, emphasizing that while Solo is a tool for deployment, it cannot be solely responsible for ensuring supply chain security. They highlighted the importance of deterministic builds and the need for security to lead efforts in ensuring components are not compromised. Nathan explained that while Solo has a solid foundation for supply chain security, external dependencies and third-party libraries cannot be avoided entirely. They agreed to continue the discussion in the next meeting, with Jeremy and Nathan potentially preparing a slide on the topic.

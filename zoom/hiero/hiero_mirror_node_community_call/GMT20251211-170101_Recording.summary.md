## Details

### Mirror Node Operations Transition Plan

The meeting focused on promoting attendance at future community meetings, with Keith acknowledging the need for more outreach to Mirror Node operators and collaboration with the marketing team. Steven discussed upcoming changes to block streams and Mirror Node operations, including the transition from record streams to block streams in early 2026, which will require Mirror Node operators to upgrade to new versions supporting the change. Keith and Steven clarified that while some operators may connect to Tier 1 block nodes, existing bucket access will be maintained with a one-month retention period, though the final decision on bucket location is still pending.

### Mirror Nodes Deployment and Transition

The team discussed the transition from block nodes to block streams and its impact on Mirror nodes and SDKs, with Keith clarifying that the interaction with Mirror nodes through SDKs should remain unchanged. Steven provided detailed instructions on setting up and running Mirror nodes, highlighting the challenges of catching up to the current state of the network and the costs involved. He outlined various deployment options, including Kubernetes, Docker, and a one-click deployment in Google Cloud Marketplace, emphasizing the ease of setup and the availability of demo data for testing.

### Hedera Consensus and Mirror Nodes

Keith explained the architecture of Hedera's mainnet and consensus nodes, noting that consensus nodes only retain transaction records for about 2 minutes before sending them to record streams. He described how Mirror nodes take these record streams and store them in SQL databases, allowing for quick API access to historical blockchain data. Steven clarified that users pay fees for submitting transactions to consensus nodes, and the data is then bundled into record files for download. He also mentioned that companies like Hashgraph, QuickNode, and Validation Cloud run their own Mirror nodes, offering both public and private API access to the data. Sophie asked about running her own Mirror node, and Keith explained that this would allow for customizable API access without throttling limitations.

### Mirror Node Data Synchronization Challenges

The discussion focused on Mirror Nodes, their data requirements, and synchronization challenges. Keith and Steven explained that while setting up a Mirror Node requires downloading 4-5 years of historical data (which can be expensive and time-consuming), there are options to start with minimal data or use filtered data to reduce storage requirements. They clarified that while full historical data is necessary for certain functions like querying account balances across the network, users can choose to sync only specific types of data or recent transactions to manage storage costs. The conversation concluded with Sophie raising a question about data consistency, which was not directly addressed in the transcript.

### Mirror Nodes: Data Verification and Access

The meeting focused on discussing Mirror Nodes, their role in the Hedera network, and how data is verified and accessed. Keith and Steven explained that while current Mirror Nodes rely on trust for data accuracy, a new version of state proofs in 2026 will allow cryptographic verification of transaction information. They clarified that Mirror Nodes download record streams in memory and insert them into a PostgreSQL database, with Angelina learning that external storage isn't necessary as the data is discarded after processing. The discussion also covered public endpoints managed by Hedera and Hashgraph, with Sophie inquiring about analytics capabilities, though Steven noted that analytics would typically require running a separate Mirror Node with a column-oriented database rather than querying public APIs. The conversation ended with Angelina seeking clarification about running Mirror Nodes on Windows, with Steven suggesting it should work in a container but noting limited testing on Windows systems.

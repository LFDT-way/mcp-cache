## Agenda

This group is meant to cover all consumers of blockstreams - block nodes and mirror nodes.

## Overview

The meeting focused on discussing the first-ever Blockstream Community Group, which was previously named the Mirror Node Community Group. The participants discussed challenges with meeting attendance and promotion, agreeing to implement multiple outreach strategies including updating the HIRO website, posting in ecosystem channels, reaching out via email and Slack to mirror node operators, and using LinkedIn to promote the group. They reviewed upcoming software releases, with Mirror Node version 160 expected in two to three weeks and Block Node version 75 introducing wrapped record blocks streaming for Tier 1 block nodes. The group also discussed the need for better documentation and tutorials to help developers test Blockstream products, particularly for those working on consensus nodes and staking functionality.

### Blockstream Community Promotion Strategies

### Node Meeting Attendance Challenges

Keith and Mark discussed challenges with meeting attendance and registration, particularly for those running mirror nodes and block nodes. They agreed to send meeting invites to node operators as a first step, with Mark offering to add this to his list. Keith outlined the dual purpose of their meetings, which include presentations on specific topics and discussions about priorities for block node and mirror node repositories, as well as opportunities for contributors to work on good first issues in the codebases.

### Community Calls Planning Discussion

The group discussed plans for community calls, with Keith explaining that while sprint planning was intended to move into these calls, it wouldn't be appropriate for this particular meeting due to its focus on both block and mirror nodes. Mark and Keith agreed to postpone Mark's presentation to the next month's meeting and instead focus on increasing participation in future calls. The discussion ended with Keith asking about current release expectations for mirror node upgrades, though this question was not fully addressed in the transcript.

### MirrorNode Version Release Update

Mark announced that MirrorNode version 160 will be released in two to three weeks, following a delay from version 57 due to state proof issues. Version 75 will include the first streaming event of wrapped record blocks to Tier 1 block nodes for testing and integration preparations. Keith noted that MirrorNode operators typically update within two weeks of a release, though concerns were raised about silent stakeholders and the need for proactive communication with major exchanges like Coinbase during critical updates.

### Mirror Node Upgrade Verification Discussion

The team discussed the need to verify Mirror Node operators are upgrading to version 160 and to explain this upgrade to Blockstream. Keith suggested creating a blog tutorial to help users test BlockNodes and Blockstream in advance of the cutover, and Nana confirmed that documentation already exists on the GitHub Blocknode repository and Hyrule docs, which includes information on connecting to mirror nodes and using solo with NLG and the simulator. The discussion concluded with Keith asking about who would need to use WRAPS for testing, particularly focusing on developers working on consensus nodes who would need to test staking and node management functions.

### WRAPs Requirements for Staking Development

The team discussed whether developers need to use WRAPs for staking-related testing and development purposes. Nana clarified that while WRAPs aren't required for basic staking functionality, they might be useful for last-mile validation and testing consensus weight calculations. Mark confirmed that most developers wouldn't need WRAPs for typical staking app development but would be necessary for Hyro contributors and developers working at a lower integration level. The group agreed to create companion documentation outlining when WRAPs are needed versus when they aren't required, and Mark suggested Keith prepare an agenda for the next meeting.

### Content Planning and Website Updates

Mark and Keith discussed preparing content for next month's meeting and agreed to schedule a separate meeting to plan communications, which should be sent out approximately two weeks before the main meeting. Keith committed to updating the website to reflect the name change to "Blockstream Community Group." No additional comments or suggestions were raised by the other participants.

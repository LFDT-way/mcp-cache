## Details

### GitHub Label Streamlining Discussion

Sophie discussed her efforts to streamline GitHub labels to improve workflow coordination following updated branch protection rules. She explained her reasoning for simplifying the labels by removing "in development" and "ready for review" categories, instead using "draft" to imply "in progress" unless marked as stale. The changes aim to reduce confusion and better align with the new requirements for merging code.

### Pull Request Review Workflow Discussion

Sophie and Robert discussed their different approaches to reviewing pull requests and drafts. Sophie explained that in their workflow, drafts are used for in-progress pull requests and those that have been rejected for review. Robert shared that in his C++ workflow, they use different labels like "needs revision" and skip over tagged items. Sophie expressed concerns about the complexity of their current labeling system, noting they had recently encountered issues with too many labels per issue, and questioned whether the current bot setup would be practical for Leslie.

### Priority Labeling System Discussion

Robert and Sophie discussed the current priority labeling system in their issue tracking, noting that priority settings don't display on the issue page, which is problematic for maintainers but less relevant for contributors. They agreed that the current system works well for contributors selecting tasks based on availability, though maintainers would benefit from better priority visibility, particularly for pull requests. Sophie decided to trial the current system for a few weeks to assess if additional labels are needed before considering bot-based solutions, while Robert indicated that while a two-step review process might be implemented eventually, current SDK resource reallocation discussions are putting this timeline in flux.

### SDK Scores Improvement Discussion

Robert and Sophie discussed the priority of improving SDK scores, noting that most are already at or near the required 7 level. They agreed that current efforts are focused on marginal gains and experimentation in the Hiero open source environment, with plans to potentially share findings with the rest of Hiero later. Sophie mentioned that the new templates are performing well based on tracked data.

### Contributor Onboarding Success Rates

Sophie presented data showing improving success rates in onboarding new contributors through good first issues, with a current completion rate of 0.41, meaning each good first issue creates approximately 0.4 new successful contributors. Robert expressed the need for more clarity on prioritization and resources, indicating that while most SDKs are seeing new contributors, finalizing the product including templates, documentation, and automation is still a few months away. Sophie mentioned plans to port over some C++ workflows and audit existing work to identify what has already been completed versus what remains to be done.

### Hiero Hackers Repo Discussion

Sophie proposed creating a Hiero hackers repo to copy existing workflows and make them on-call, which would eliminate the need to maintain much custom code. Robert agreed with the long-term approach but raised concerns about potential security issues related to cross-repo access. They discussed the possibility of creating a dedicated Hiero repo for automation instead, which could be accessed by other repositories and would require proper configuration for widespread adoption.

### Repository Workflow Standardization Discussion

Robert and Sophie discussed standardizing repository workflows to create a more consistent contributor experience across different repositories. They agreed to start with a proof of concept using an on-call solution before potentially implementing a GitHub app for greater complexity. Daniel suggested creating a dedicated repository to handle CI/CD pipeline workflows, which would allow for better organization and potentially be implemented across all repositories.

### Auto-Assign Feature Discussion

Sophie clarified that while a prototype isn't strictly required, having one could be beneficial, and recommended reviewing the issue description and attending a mentorship call for more specific information.

## Details

### Guidelines for Inactive Pull Requests

The team discussed guidelines for handling inactive pull requests, particularly for good first issues. Robert shared that he gives contributors 4-5 days to respond before threatening closure, aiming for a week maximum for good first issues. Sophie mentioned using specific labels like "requires developer revision" and "requires developer activity confirmation" to clearly communicate the status to contributors, and noted that reactivating closed PRs has been unsuccessful. The group agreed that automation could be beneficial for managing these timelines, though current systems only have a generic 21-day setting that could be optimized by difficulty level.

### JavaScript SDK Contributor Management

Sophie reported that she has been trying to keep up with the JavaScript SDK organization but cannot fully support the automation task at the moment. Robert inquired about updates on moving the automation suite to the Hiero hackers group, but Sophie had not heard any progress on this. They discussed the idea of requiring contributors to complete a good first issue in any repository before allowing them to work on beginner issues across different repositories, though Robert raised questions about the technical feasibility of implementing this at an organizational level.

### Workflow for Assigning Good First Issues

Sophie and Robert discussed implementing a workflow to assign good first issues based on a contributor's previous completion history. They agreed to use a GraphQL query to check if a user has completed at least two issues, with the option to fall back to general Hiero issues if specific SDK issues aren't available. Robert confirmed the current workflow uses GraphQL queries and suggested it would be straightforward to modify to check across multiple repositories. The discussion also touched on ensuring contributors understand requirements like DCO and GPG signing when working on different repositories.

### Optimizing GFI Workload Distribution

Sophie and Robert discussed the requirements for good first issues (GFIs) and DCO/GPG signed commits across repositories. They agreed that requiring multiple GFIs could help distribute workload across repositories and encourage exploration of different SDKs. The conversation also touched on the challenges of managing changelogs, particularly in the Python SDK, and the potential benefits of requiring changelog entries for upskilling contributors. They concluded that linking to Hiero-wide GFI opportunities could be an effective solution, combining available local GFIs with broader repository options.

### Repository Integration and Contributor Experience

The team discussed integrating an existing repository with a website to improve contributor experience, particularly around issue tracking and automated notifications for merged pull requests. Robert agreed to document the discussed improvements and explore potential venues for further discussion, possibly in a future community management meeting. The group acknowledged time constraints and planned to continue the conversation in more detail at a later meeting.

## Overview

The Solo Action Community Meeting focused on technical discussions around Docker developments, TypeScript code analysis warnings, and workflow action restructuring. A prototype Docker container for running Hiero solo action tests locally was presented, with the team agreeing to continue discussions about framework architecture and gather community feedback through surveys.

## Details

### Docker and Cleanup Discussion

The Solo Action Community Meeting began with Hendrik introducing a topic about Docker developments, which he planned to discuss later. Jessie raised an issue regarding cleanup tasks, but Hendrik suggested addressing it after his Docker presentation. The meeting participants agreed to follow this order, with Hendrik presenting his Docker updates first, followed by Jessie's cleanup topic.

### TypeScript Code Analysis Warnings

Jessie discussed issues with code analysis warnings in TypeScript, particularly related to error handling and type inference. Despite making changes to method naming and error handling practices, the warnings persisted. Hendrik suggested searching online for specific solutions to the TypeScript warnings, noting that while they were warnings rather than errors, Jessie could still investigate further.

### Workflow Action Restructuring Discussion

Hendrik and Jessie discussed the restructuring of actions in their workflow, focusing on the creation of composite actions and the setup process for tools like Kind and Java. Jessie explained the separation of actions into a main action for testing and a composite action for setting up the environment. Hendrik raised concerns about the need for multiple actions in the workflow, which he felt was inefficient. Roger, who had been researching the REST SDK, acknowledged the issue and agreed to look further into node actions to understand their limitations better.

### Repository Action Management Strategy

Andrew and Hendrik discussed the strategy for managing actions and dependencies in their repository. They agreed to avoid creating new actions within a repository to prevent unintentional dependencies on their code. Instead, they proposed using shell scripts in a separate folder to automate tasks, which would allow more control over the environment and prevent external users from relying on their actions unintentionally. Hendrik suggested exploring the Solo team's approach to setting up Zolo, as it might provide a more efficient way to manage installations and cleanups.

### Solo GitHub Action Integration Discussion

The team discussed integrating Solo commands into their GitHub action workflow. Hendrik proposed working with the Solo team to create a single command that can install and uninstall all necessary components, allowing for clean removal on self-hosted environments. Jessie agreed to contact Jeremy from the Solo team for further discussion, while Roger suggested reaching out through Discord channels. Georgi raised concerns about potential redundancy with the new Solo quick-start command, but Hendrik assured that their current approach would not be duplicated, focusing instead on providing configuration options and flexibility.

### Solo Action and Quick Start Alignment

The team discussed the alignment between the solo action and the solo quick start functionality. Roger noted that the current solo quick start single deploy meets expectations but identified a small difference in implementation regarding node version settings. Georgi expressed concern about potential duplication of work between the solo action and the solo team's features, suggesting the need to define unique value propositions for the solo action. Hendrik proposed forwarding necessary information to the solo team to discuss the integration of the quick start into the solo action, aiming to reduce complexity and focus on core functionalities.

### Solo Quick Start and Roadmap

The team discussed the Solo quick start action and its documentation. Hendrik raised the need for a config parameter to define the Mirror Node version, which Roger confirmed would be addressed in the next release. They agreed that a presentation of the Solo roadmap would be beneficial, as it would provide clarity on planned features and updates. Roger highlighted the existing Solo community resources, including the Discord channel and documentation website, while noting that the roadmap was currently missing.

### Docker Proposal Discussion Postponed

Hendrik discussed a proposal for a Docker container to replace a GitHub action, but the solo team preferred keeping it within the solar repo. He mentioned ongoing discussions about where the project should be hosted, and decided to wait for resolution of these discussions before moving forward.

### Docker Prototype for Local Testing

Hendrik presented a prototype of a Docker container for running Hiero solo action tests locally. The container sets up a cluster and can execute unit and integration tests against it. He demonstrated creating an account and performing transactions, though some functionality was not yet tested. Georgi inquired about port access and dynamic address book functionality, which Hendrik confirmed were currently limited but could be expanded in the future. The prototype provides a faster testing environment than the existing GitHub action, running directly on the user's machine.

### Solo Test Framework Accessibility Discussion

The team discussed the solo test framework and quick start environment, with Hendrik emphasizing the need to make it accessible for new users at hackathons and community events. Roger shared his experience using the solo quick start locally and expressed some concerns about the separation of components, though he agreed with the overall approach. The group agreed to continue the detailed discussion about framework architecture in a future meeting, and Georgi suggested creating a survey to understand how different SDK developers prefer to use the framework. Hendrik supported this idea and emphasized the importance of gathering community feedback before making any major decisions about the framework's development.

### GitHub Permissions for Python SDK

The team discussed GitHub permissions and team management for the Python SDK project. Sophie learned how to create and manage teams, including setting up triage permissions, while Andrew clarified that triage permissions allow reviewers but not write access to the repository. Hendrik explained that a code owners file could help automatically assign reviewers based on file ownership, though this feature was not currently implemented in the Python SDK. The discussion highlighted some limitations in GitHub's security features and suggested improvements for better reviewer assignment processes.

### GitHub Reviewer Assignment Features

The team discussed GitHub's automatic reviewer assignment feature, which adds team members to pull requests based on file changes. Andrew explained that if a user is part of multiple teams, they will be added once to the review and can approve for all teams they belong to, but separate approvals are still needed from different teams. Sophie learned that while basic GitHub configuration doesn't support label-based reviewer assignments, this could be achieved with a custom GitHub action or app. The discussion also covered project boards, which allow teams to organize issues into different categories like backlog, to-do, and work, with the triage permission enabling the ability to modify these boards.

### Good First Issue Labeling Discussion

The team discussed the labeling process for good first issues and debated the responsibilities of maintainers, with Hendrik clarifying that contribution quality, not hours worked, determines a maintainer's role. Sophie proposed creating a good first issue triage committee to help reduce maintainer workload, and suggested making monthly maintainer meetings bi-weekly to increase participation. The team agreed to continue these discussions in future meetings, with no immediate decisions made on the labeling process or meeting frequency.

### Maintainership Criteria and Project Needs

The group discussed the criteria for maintainership, emphasizing that while maintainers should be active contributors, the frequency of contributions is not the sole determinant. Hendrik clarified that maintainers should be those who care the most about the project, and the role involves more than just making contributions, such as reviewing PRs, merging PRs, and participating in repo maintenance. Sophie and Hendrik agreed that different projects may have varying needs, and some may opt into using good first issues, while others may not have the resources to do so. Hendrik also noted that Hashgraph is interested in implementing good first issues for their SDKs to grow the community but does not plan to use them for other projects.

### SDK Good First Issues Strategy

The team discussed implementing good first issues in SDK repositories, with Hendrik clarifying that while some SDKs have shared maintainers, they decided to start with SDKs as the easiest entry point before expanding to other repositories. Sophie inquired about the good first issue template and governance repository, which Hendrik confirmed was a topic for future discussion. The team agreed to develop a solid strategy for good first issues in SDKs first, with Robert suggesting they would learn from the process and potentially apply it to other repositories in the future.

### GitHub Issue Template Enhancements

The team discussed improvements to GitHub issue templates, with Sophie explaining she made two pull requests to fix and enhance the templates, addressing previous issues like duplicate headlines. Hendrik and Jessica approved the changes, and Sophie proposed creating custom templates for each SDK repository to better suit their specific needs, while Hendrik suggested exploring whether local templates could override the generic ones. The team agreed to create new good first issues, particularly for the Java SDK, and Sophie committed to working on custom templates for the JavaScript SDK.

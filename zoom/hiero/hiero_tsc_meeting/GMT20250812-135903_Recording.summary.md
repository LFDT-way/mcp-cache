## Details

### Hierarchical TSC Meeting Overview

Hendrik welcomed attendees to the Hiero TSC meeting, emphasizing its open and public nature and encouraging participation under the Linux Foundation's code of conduct and antitrust policy. He noted that the meeting was well-attended, with consistent attendance over the past weeks, and expressed hope for continued engagement from new participants.

### Hiero CLI Project Review

The team reviewed the Hiero CLI project proposal, which Michiel had updated with detailed information including project history, architecture, and contributions. Michiel presented the project's structure, which includes command, business, and API layers, as well as state management features rewritten by Michael Bennett. The team agreed to vote on the proposal, with Richard confirming he would move it forward after the vote.

### CLI Tool and Solo Discussion

The team discussed the CLI tool's differences from Solo, with Richard explaining that Solo allows deploying entire networks while the CLI is more full-featured for network operations. Michiel mentioned Michael Bennett's work on Solo support and dynamic network capabilities. The team approved the CLI project with 6 votes in favor, and Michiel confirmed he would join the Hiero community transition meeting that day despite being on a team off-site. Hendrik noted that the Hiero project's official pull request for graduation had been submitted and was awaiting review, with the first comment being positive.

### HIP Tracker and Review Process

Richard presented a new HIP tracker he created to help keep track of all HIPs and their statuses. He explained the different stages of HIPs, from draft to final, and demonstrated how the tracker would help the team manage and review HIPs more effectively. Richard identified three HIPs ready for review or voting, including one that may have been presented but not properly documented. The team agreed to prepare and present these HIPs during the meeting, with the goal of getting votes on them.

### Fee Account Proposal and Updates

The team discussed a proposal for a new fee collection account (80280) that would be governed by the network code and used to simplify fee distribution and reduce transaction overhead. Richard explained that this change would improve performance and scalability by reducing the number of accounts involved in transactions from 5-6 to 3-4, and clarified that the account would have no keys due to legal considerations and the fact that it's owned by the network rather than any specific entity. The proposal received unanimous approval from the team members present. Richard also mentioned a separate proposal to add a stale status code, which he planned to present for voting in two weeks, potentially requesting an expedited vote the following week to support performance testing for version 0.65.

### Stale Event Handling in Consensus Layer

Richard explained the consensus layer's design and the concept of stale events, which occur when transactions fail to gain sufficient network visibility within a configured time limit. He described how the network handles stale events by keeping them in an "unknown" state until they timeout after 3 minutes, and proposed adding a new "stale" status code to help developers identify and potentially resubmit stale transactions more quickly. Richard noted that while this HIP (Hedera Improvement Proposal) is relatively straightforward, there are some complications regarding transaction state transitions and duplicate transactions that need further consideration.

### Simplifying Fee Computation System

Richard explained the complexity of the current fee system and the proposed simplification through a new HIP. He described how the current system involves complex calculations and configurations, which the new system aims to reduce by simplifying fee computation to a basic fee schedule in USD. Richard also clarified that transactions would have a base fee plus additional charges, comparing this to the process of ordering a pizza, which was the simplified model they aimed for.

### Hiero Fee Structure Overview

Richard explained the fee structure in Hiero, which consists of a base fee and additional components. He clarified that from a user's perspective, the fee breakdown into node, network, and service components is an implementation detail. Richard outlined user stories for various stakeholders, including app developers, Hiero developers, H Bar holders, auditors, and node operators, emphasizing the importance of clear fee breakdowns and correct fee calculations. He also described the fee distribution process, highlighting the roles of node fees, network fees, and service fees in compensating nodes for their work in transaction processing and storage.

### Transaction Charging Structure Overview

Richard explained the charging structure for different types of transactions, including unreadable, invalid, and unhandled transactions, as well as congestion pricing. He detailed how the configuration is done through a JSON file, with sections for extras and node network service. Richard also described the various extras that can be charged, such as transaction signatures, bytes, and custom fees, all defined in tiny cents for precision.

### Hiero Transaction Fee Structure

Richard explained the fee computation structure for Hiero transactions, where node and network fees are based solely on bytes and signatures to ensure fair treatment of all transactions and incentivize correct node operation. He outlined how service fees are configured, allowing for modular customization of transaction and query pricing, with the flexibility to define free queries and optional extras. Richard also mentioned an inconsistency between an example and the schema that needs correction, and introduced a new API for mirror nodes to estimate fees.

### Unified Fee Estimation System Update

Richard explained the fee estimation process for transactions, detailing how users can submit transactions in JSON or Protobuf format to receive fee estimates. He described the complexity of fee calculations, which depend on both intrinsic transaction properties and the current state of the system. Richard introduced a new query parameter called "mode" that allows users to specify whether they want to include state in the fee estimation. He emphasized that this new system will improve performance and accuracy by using a unified fee engine across different applications. Richard concluded by stating that the implementation is nearly complete and will be ready for voting in a few weeks, with the goal of finishing before the end of the year.

### Block Nodes: Enhancing Network Architecture

Nana presented an overview of block nodes, a new type of Hiero network node designed to improve data availability, decentralization, and client diversity. Block nodes will sit between consensus nodes and mirror nodes, receiving block streams from consensus nodes and making them available to other nodes and clients. They will also handle state proofs, state snapshots, and reconnection logic, allowing consensus nodes to focus on transaction processing. Block nodes will support filtered block streams, enabling operators to customize the data they store while maintaining the ability to verify the network's history.

### Hyperledger Block Node Implementation Proposal

Nana presented a new HIP (Hyperledger Implementation Proposal) for block nodes, which allows different operators to run their own nodes and enables builders to create custom APIs. Mark highlighted the benefits for mirror node operators, as block nodes would replace cloud buckets with a decentralized data lake, reducing costs and complexity. Alex clarified that tier-one block nodes are crucial for network operations, while tier-two and beyond nodes are supplementary. Nana explained the discovery mechanism for block nodes and mentioned that more details would be covered in HIP 1137. May asked about the impact on existing apps, and Nana explained that most apps would only need to update their mirror nodes to support the new architecture, with options for more customization at higher tiers.

### Consensus and Block Node Architecture

The team discussed the architecture of consensus and block nodes, clarifying that applications would continue to interact with consensus nodes for transactions and queries, while also reading from mirror and block nodes. Nana explained that while block nodes at tier one would initially be operated by consensus node runners, the system would evolve to allow every consensus node to have its own block node for low latency. May raised questions about data consistency and potential malicious behavior, which Nana addressed by explaining that the TSS (Threshold Signature Scheme) verification process ensures that only agreed-upon information is pushed out by consensus nodes, preventing malicious nodes from introducing incomplete or incorrect data.

### Block Node Deployment and HIP 1127

The team discussed tier one block nodes, with Brandon inquiring about hardware and geographical deployment requirements. Nana confirmed documentation is being developed, while Leemon explained that block nodes require similar hardware specifications to mirror nodes, with the main difference being reduced processing power. Leemon also clarified that block nodes will be operated by council members, with each running both a mainnet and a block node, and explained how the system ensures data integrity through cryptographic proofs. Michael then presented HIP 1127, which aims to simplify the protobuf messages in the block stream by removing unnecessary layers, while maintaining compatibility with existing mirror nodes.

### SDK Publishing and Transition Plan

The team discussed the Hiero SDK publishing plan, with Simi presenting the timeline for dual publishing of JavaScript and Rust SDKs, and the hard cutover for Java SDK. They agreed to start dual publishing for JavaScript at version 2.70 and for Rust at version 0.38, with Java transitioning at version 2.80 after a 9-month notice period. The team decided to create a blog post about the SDK roadmap and future, with Keith volunteering to help drive this communication. They also discussed measuring adoption rates of the new SDK versions, with Roger confirming they could track downloads from NBM and Create Setio.

## Overview

The TSC meeting focused on voting for two HIP proposals related to transaction signatures and governance account sizes, with HIP 1200 being approved unanimously. The team discussed various technical aspects including transaction size limits, address book evolution, and node operation rules, with particular attention to node IDs and account management. The conversation ended with discussions about improving community call infrastructure, including proposals for better organization of meeting recordings and agendas.

## Details

### TSC Approves HIP 1200

The TSC meeting began with Richard presiding and reviewing the agenda, which included voting on HIP 1200, the threshold signature scheme, and HIP 1300, increasing transaction size for governance accounts. The TSC approved HIP 1200 with a 7-0 vote, and Mark inquired about the status of the internal review for HIP 1300, to which Richard confirmed it could proceed. The conversation ended with Richard mentioning that any additional business could be discussed in the Zoom chat, and Keith raised a topic about community calls, which was deferred to the end of the meeting.

### Privileged Account Transaction Limit Proposal

The meeting focused on a proposal to allow larger transactions for privileged accounts on the network, specifically accounts 002 and 0050, to address the 6KB transaction size limit. Richard explained that this would be achieved by using the same jumbo transaction size as Ethereum transactions, and clarified that there are no size limits on accounts themselves, though there are caps on the number of keys attached to an account. Alex raised a question about extending the privilege to other accounts like 50A, which Richard agreed was a good idea to consider. The group discussed the safety and performance implications of the change, with Richard confirming that it poses no significant risks.

### Dynamic Address Book Phase 3

Richard explained the evolution of the system's address book, from a static file to a dynamic on-chain data structure that allows nodes to be added or removed and stake weights to be adjusted on a monthly basis. He described the upcoming "Dynamic Address Book Phase 3," which will enable daily updates during staking reward calculations, allowing node operators to associate different account IDs with their nodes for reward distribution purposes.

### Node Operator Transaction Fee Responsibilities

Richard explained that node operators are responsible for paying fines and fees associated with transactions processed by their nodes. He described two scenarios where nodes might be fined: if they fail to perform due diligence checks on transactions, or if a transaction is valid when submitted but becomes invalid due to key changes in the account before consensus is reached. In the latter case, the node is held responsible for the fine even though it didn't do anything wrong, as the network cannot distinguish between user error and node error.

### Account ID Change Rules Discussion

Richard explained a proposed HIP that clarifies rules around changing account IDs on nodes, addressing various scenarios such as sync requirements, zero funds, and account deletion. He emphasized that the HIP specifies behavior in these cases, distinguishing between node operators and account owners. Alex raised a concern about the uniqueness of node accounts, noting that previously it was communicated that accounts could be reused across multiple nodes for treasury management. Richard acknowledged this point and explained that the motivation for uniqueness was to prevent a large number of nodes from going offline simultaneously due to a single account balance issue, which could potentially disrupt the network.

### Node Account ID Sharing Proposal

Richard explained the current system where transactions specify a node account ID and discussed a proposed change to allow multiple nodes to share the same account ID. He noted that this could cause issues with in-flight transactions if a node's account ID changes. Richard also mentioned an upcoming update to transaction specifications that would allow transactions to specify a list of node IDs, which would decouple transactions from specific nodes and make the system more robust.

### Hedera Node ID Changes Discussion

Alex discussed Hedera's network rules limiting node operation concentration and the upcoming changes to node ID versus node account ID, noting that using node ID is more stable for transaction processing. Richard agreed to leave the information in the PR, and Alex expressed his desire to get the project across the finish line while avoiding unnecessary roadblocks.

### Node ID Security for Transactions

Richard explained the necessity of including a node ID in transactions to prevent dishonest nodes from stealing transaction fees. He described how without a node ID, malicious nodes could intercept transactions and claim rewards for them, potentially leading to duplicate transactions and financial abuse. Keith added that the node ID system allows users to specify trusted nodes for transaction submission, providing an additional layer of security and control.

### Community Call Infrastructure Improvements

The team discussed improving the infrastructure for community calls, focusing on better organization of meeting recordings and agendas. Jessica suggested using the governance repo to host meeting agendas, similar to other LFDT infrastructures, and proposed adding more detailed information to the Hiero Ledger GitHub organization landing page. Brandon recommended creating a markdown document with easy-to-follow instructions for accessing community call information. The group agreed to explore these options further, with Jessica planning to discuss the agenda hosting solution with David and update the landing page with relevant information.
